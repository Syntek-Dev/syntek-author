# STEPS.md — update the tracker

**Last Updated**: <%DATE%> **Version**: 0.1.0 **Maintained By**: <%AUTHOR_NAME%>
**Language**: British English (en_GB)

The short procedure for keeping the tracker true. Run it every time something happens with a
reader. Each step names the guide it uses. **Run in order** — the ordering is load-bearing — and
tick `CHECKLIST.md` as you go.

> Read this folder's `CONTEXT.md` and `CLAUDE.md`, then the tracker itself (its path is in
> `proposal/src/CONTEXT.md`) and its `## Rules`. No skill runs this procedure: it is record-keeping.

## 1. Read the tracker

> **Skill:** — · **Guide:** `proposal/src/CONTEXT.md`

Find the row, or confirm there is none. Never work from memory of an earlier session. _Mechanical._

## 2. Establish what actually happened

> **Skill:** — · **Guide:** the package anatomy in `proposal/docs/reference/`

Ask the author where it is not clear. An approach that was **drafted** leaves the row at its first
status; one the **author sent** moves it on, dated to when the author sent it. _Substantive._

## 3. Update or create the row

> **Skill:** — · **Guide:** the package anatomy in `proposal/docs/reference/`

Fill every column the tracker has, and use only the statuses its `## Rules` list. _Mechanical._

## 4. Record a reply exactly as it came

> **Skill:** — · **Guide:** `proposal/docs/reference/approaching-readers.md`

Do not upgrade it. A warm maybe is not a yes; a request for more is not an offer. Quote the
operative words in the row. A tracker that flatters itself is worse than none, because decisions
get made on it. _Substantive._

## 5. Keep anything received verbatim

> **Skill:** — · **Guide:** the package anatomy in `proposal/docs/reference/`

An endorsement, a reason for a pass, the terms of a request: attributed, dated and stored where the
anatomy guide says, in the giver's exact words. **Never edit it for length or polish** without
their agreement. _Substantive._

## 6. Report a yes or an offer at once

> **Skill:** — · **Guide:** the package anatomy in `proposal/docs/reference/`

Tell the author now, not in the hand-back. What follows (sending what was promised, telling others
still considering the book) is the author's to do, and the anatomy guide says what is expected.
_Substantive._

## 7. Set the next action and its date

> **Skill:** — · **Guide:** the package anatomy in `proposal/docs/reference/`

**Every open row has one,** or the row is closed. Use the chase rule the anatomy guide sets; after
it is spent, the row is marked lapsed rather than left waiting. _Substantive._

## 8. Append corrections; never overwrite

> **Skill:** — · **Guide:** `proposal/src/CONTEXT.md`

If an earlier entry was wrong, append a dated correction under the tracker's `## Corrections`
rather than editing the history. _Mechanical._

## 9. Reconcile the package

> **Skill:** — · **Guide:** `proposal/workflows/01-assemble-the-proposal/STEPS.md`

If the package's account of its readers now disagrees with the tracker (a name has declined, a list
is exhausted, a new reader has emerged), **the tracker is right.** Flag the part for updating
through `01-assemble-the-proposal`. _Substantive._

## 10. Hand back

> **Skill:** — · **Guide:** `proposal/src/CONTEXT.md`

One line per change, plus **everything falling due soon**: a chase this week, a promised sample, a
yes waiting on a chapter that does not exist yet. That list is the point of the tracker.
_Substantive._
