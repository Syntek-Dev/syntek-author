# DESIGN.md — syntek-author

**Last Updated**: 16/10/2026 **Version**: 0.4.0 **Maintained By**: Syntek Studio
**Language**: British English (en_GB)

The build contract for `syntek-author`, a Copier template that generates writing repositories in three variants:
`theology` (Christian non-fiction books), `fiction` (novels, with optional worldbuilding and a constructed-language kit) and `business` (business, legal and client documents).
It generalises three hand-built repositories and follows the house Copier idiom of `syntek-base`.

This file is the template repository's own design record. It sits outside `template/`, so it is never rendered.
Where this file and the cross-check map disagree, **this file wins**. Every override is marked **(overrides cross-check)**.

**Source material** (read-only; never modify):

| Abbreviation | Source |
|---|---|
| AT | a hand-built theology book repository (private) — the most mature example of the house layer idiom |
| SC | a second, older theology book repository (private) — sensitive-content handling and the sections layout |
| BD | a hand-built business-documents repository (private) — the `library/` and `planning/` layers and LaTeX deliverables |
| SB | `syntek-base` (public, `gh:Syntek-Dev/syntek-base`) — the house Copier idiom |

The private sources are named and located only in the maintainer's local notes, never in this repository. Convention maps written from them during the build (house formats, verbatim skeletons, hazards) are kept outside the repository too.

| D9 | **A unit and its sections.** A *unit* is a chapter (books) or a document (business). A *section* is a small passage inside a unit, typically 300–500 words: one argument step, one scene beat, one clause group. The unit's **plan** lives in `planning/src/units/NN-kebab-title.md`; the unit's **prose** lives in the content layer and is assembled from promoted sections. | **(overrides cross-check 1.1(i))**: the stub's brief moves out of the manuscript file, so promotion never mixes plan and prose. |
| D10 | **The authoring loop**, as designed in conversation: `draft-section` (the AI drafts one small section) → `adapt-section` (the author's notes, or edits, drive a targeted revision with alternatives for contested lines) **or** `improve-section` (the author drafts; the AI proposes changes as a diff with a one-line reason each, at strength `light`, `edit` or `rework`) → `promote-section` (the author's word moves the approved section into the unit and records provenance) → `learn-voice` (mines the ledger and proposes voice-note additions the author approves). | **(overrides cross-check 4.1)**, which redefined `adapt-section` as source adaptation. |
| D11 | **Two status vocabularies.** The **unit** status ladder: `idea · outlined · draft · structural-review · fact-check · line-edit · final` (in the unit brief's frontmatter; `stub` is an accepted alias of `outlined`). The **section** status: `ai-draft · author-draft · adapted · improved · author-revised · promoted`. A unit becomes `final` only through the review workflow and the author's word, never through `promote-section`. Gates (`standards/verification/verification.md`): **V1** brief agreed (gates `idea → outlined`); `outlined → draft` needs only V1 held and happens when the first section is drafted; **V2** every planned section promoted with zero flags, and **V3** the unit proof builds (together gate `draft → structural-review`); **V4** structure review (gates `structural-review → fact-check`); **V5** fact-check (gates `fact-check → line-edit`); **V6** comprehension, flow, grammar and spelling passes plus the author's word (gates `line-edit → final`). Variant sub-gates hang off V4–V6. Workflows cite a gate as `V2 (draft → structural-review)`. | |

| D20 | **SVG → font in v0.1.** `tooling/font.py build <lang>` compiles `script/glyphs.toml` + `script/glyphs/*.svg` into `build/fonts/<lang>.otf` (CFF outlines via fontTools `FontBuilder` and `svgLib`). | D31 | **Books typeset through LaTeX.** The author writes Markdown; the `typeset` skill turns a promoted unit into `typeset/src/units/NN-kebab-title.tex` by (1) running Pandoc with the house Lua filter to produce the base — **the words come from Pandoc, never retyped by the AI** — saved as `typeset/src/units/.base/NN-kebab-title.tex`; (2) applying styling with house-class macros only; (3) `make tex-check` (`tooling/texcheck.py`, stdlib) compares the styled file's words against the Markdown's words and fails on any difference. | D32 | **The conlang method** (author's 23 rules) is the governing method for `build-language`, `add-word`, `design-script`, `create-name` and the conlang tooling: world first (each language links to a culture; vocabulary depth follows what its speakers value); proto-language first, daughters derived by ordered regular sound changes (Tolkien method); 20–35 phonemes; IPA first, separate readable romanisation (no apostrophe soup, sparing diacritics, one spelling per sound with documented exceptions); phonotactics carry the flavour; one stress rule; a few allophones; word order and morphology type chosen together; decide what the language marks and what it ignores; irregularity in the most frequent words; core list first (about 200 core concepts plus pronouns); derive from roots, affixes and compounds; word histories (root → sound-shifted form → semantic drift); loanwords adapted to phonotactics; imperfect overlap with English; irregularity emerges from sound change rather than hand insertion; dictionary and grammar from day one, under version control; names consistent with the language; restraint on the page; test pronounceability aloud. The full text lives in `world/docs/reference/building-a-language.md`. | From conversation, 03/10/2026. |
| D33 | **Every language has real-world models**, as Tolkien's do (Quenya: Finnish, Latin, Greek; Sindarin: Welsh; Khuzdul: Semitic). `language.toml` carries one or more `[[inspiration]]` entries (language, period, family, weight, what is borrowed, sources). The inspiration is chiefly about **how the language sounds** — phonology, phonotactics, stress and rhythm, and so how readers hear its names — with morphology type, syntax and naming habits as optional extras. Borrow **structure and flavour**, not vocabulary: words are still built from the language's own roots; a deliberate echo of a real word is recorded in the word's `echo` field with the real word, its verified meaning and a source. Every claim about a real language is researched and cited (`research` skill → `research/src/setting/`), never asserted from memory. Related peoples share or descend from related models, so a family reads as a family (`make family` prints the tree with each branch's models). Safeguards: a false-friend check for prominent words (unintended meanings in the model languages or English slang), and respect for living languages (taking a minority, Indigenous or sacred language's feel is acceptable; lifting its words, sacred terms or caricaturing it is flagged — the rule lives in `standards/risk/FICTION.md`, `build-language`, `add-word`, `create-name` and `design-script` apply it every time, and `sensitivity-pass` adds a dedicated pass when that option is on). Three layers are decided separately: **sound** (always modelled on the inspiration), **romanisation** (a reader-facing choice: English-friendly by default, with only a few model-flavoured spellings, because readers pronounce with English habits), and **native script** (optional, with its own inspiration in `script/glyphs.toml` `[meta.inspiration]`, which may come from a real script family unrelated to the sound model — Sindarin sounds Welsh but is written in Tengwar — taking its structure without copying its glyphs). `make lexicon` warns when a language has no inspiration. The grilling skills open language and word work with the inspiration and its point in history (Section 5.2). | From conversation, 03/10/2026. |
| D34 | **The AI proposes models from the world, then gives its opinion.** Before proposing a sound model, a script or a name style, `build-language`, `design-script`, `create-name` and the grilling skills read the world files: the **people** (`world/src/peoples/`: physiology that constrains speech), the **culture** (values → where vocabulary runs deep; social structure → honorifics; religion → sacred registers; technology and materials → the script's medium), the **world history** (`world/src/history/`: eras, migrations, conquests and contact → proto/daughter splits, loanwords, when sound changes happened) and the **places** (climate, terrain, neighbours). They then present **two or three options**, each with a real-world language (or script family) and period, the reasoning tied to named world files, what readers will associate it with, a few sample names, and risks — and **state a recommendation with its reason**. If the world files are too thin to justify a choice, they say what is missing rather than guess. Always flagged: modelling a hostile or 'evil' people's language on a real ethnic group's language (readers carry the association back to real people; harsh-consonant stereotypes are a trap) — suggest ancient or extinct models, or blends, for antagonists. **Scripts take real-world inspiration by default** (recommended, not mandatory), chosen from the culture's medium and tool and the script's origin (native invention, borrowed from a neighbour, or adapted — awkward fits create authentic spelling quirks), taking a real family's structure and stroke logic, never its glyphs. | From conversation, 03/10/2026. |

## 5. Skills

Frontmatter and body follow SB conformance: `name` equals the folder; `description` ≤ 1,024 characters naming the job, its triggers, and `Not X (`other-skill`)` boundaries; H1 `# Skill: <Name> (<%PROJECT_NAME%>)`; locale line `Locale: en_GB · <%TIMEZONE%> · dates DD/MM/YYYY.`; `## Governing procedures (route here — do not restate at length)`; steps each ending `*Complete when:*`; `## Anti-patterns`; `## Cross-references` last. ≤ 300 lines including the mode file's share of the job.

Every moded `SKILL.md` carries this paragraph verbatim before step 1:

> **Mode.** Before step 1, read the doc-type mode file beside this one — exactly one of `THEOLOGY.md`, `FICTION.md`, `BUSINESS.md` ships in this folder. The mode owns the domain (paths, unit, extra reads, domain rules, examples); this file owns the procedure. Where they disagree, the procedure wins and the disagreement is reported to the author.

**Shared skills (D51).** The seven shared working-practice `SKILL.md` files (Section 5.2) are exempt from the tokens above: the H1 is `# Skill: <Name>`, the locale line names no time zone (`Locale: en_GB · dates DD/MM/YYYY.`), and the text says 'the author' or 'the owner'. Every other rule of this section applies. Every shared skill carries a neutral Mode paragraph instead, verbatim, because a companion template ships mode files of other names in the same folder; `grill-me` and `wait-what` carry it too, although this template ships no mode file beside them (a session that finds none has none to read):

> **Mode.** Before step 1, read the mode files beside this one (the upper-case `.md` files in this folder) that the project's rules route the work at hand to; where they name none, read every one. A mode file owns the domain (paths, the unit of work, extra reads, domain rules, examples); this file owns the procedure. Where they disagree, the procedure wins and the disagreement is reported to the owner.

A mode file still applies only where its `SKILL.md` carries one of the two paragraphs (D41).

**Language and word surfaces (fiction, conlang).** When `grilling`, `grill-me`, `grill-with-docs` or `wayfinder` is used on a language, a name or a word, the questions open with **the real-world inspiration and its point in history** before anything else, because they gate phonology, spelling and naming:
- *Which* real-world language or languages, and *which period* (for example Old English c. 900 against Middle English c. 1350 against modern English) — the period must sit sensibly with the language's place in its family (a proto-language leans older than its daughters).
- *What it should sound like*: what is borrowed from each model — sounds, syllable shapes, stress and rhythm first; grammar type and naming habits optionally — and *how strongly* (primary, secondary, accent).
- Only after the sound is settled, and as separate questions: the **romanisation** (how it is spelt in English prose; English-friendly by default) and, in `design-script`, the **native script** and its own optional inspiration.
- For a word or name: which model language and period gives it its flavour or echo; whether it is inherited, an early loan, a late loan or a fresh coinage; and *when in the world's own history* it entered the language (which sound changes it has been through: `stratum` and `entered_after`).
Each question carries a recommended answer with its reason, as the grilling engine requires. Facts about real languages are never settled by grilling: they go to `research` and are cited. On a branch in the target repository: run the advisory `adopt/<kind>.sh` from this repository (report by default; `--apply` performs only moves with exactly one correct destination: `workspace/{handoffs,learning}` → root; `workspace/maps` → `planning/src/maps`; `standards/style/voice-and-tone.md` → `standards/style/voice-notes.md`; chapter stub briefs → `planning/src/units/`; flat `docs/*.md` → `docs/project/`; bespoke workflows → `workflows/local/`; `status: stub` → `outlined`; `§` → `Section`), then
`uvx copier copy --trust --overwrite --data-file <answers> --data SEED_EXAMPLES=false <template> .`, review `git diff`, recover any project text into `docs/project/`, `workflows/local/` or `.claude/CLAUDE.md`, and commit the answers file.
Seeds (`.claude/CLAUDE.md`, `MEMORY.md`, `settings.json`, `README.md` and the rest of Section 3.1) are never overwritten, because they already exist. A kept `settings.json` gains only the hook entries and deny and ask rules of `migrations/family-refresh.json` (D51), and its `autoCompactEnabled: false` where the key is absent, add-only and into its own text: from the moving copy's `baseline` task, or from the first update after an additive copy. A kept `.mcp.json`, and a kept client file the answers name, gains only the two D54 servers, once each, the same way; a git-ignored one is never read, and the report names what to add by hand.
A moving adoption runs the copy tasks, including the one that records the render for the update report (D52); the additive copy (`--skip-tasks`, D41) does not, so its first update renders the recorded version itself. Either way, a repository's own skill at a shared working-practice path (D51) is kept by the copy and never refreshed.
An adopted repository usually holds tracked binaries, so `adopt.sh` and the example answers pass `DATA_STORE: repo` (D50), where a fresh copy would default to `external`, unless a sibling template's answers file there already records a store: then `adopt.sh` omits it, so the sibling's store applies, says so, and copies that answers file into its preview; an `--answers` file that records `DATA_STORE` is the copy's own answer, so `adopt.sh` then passes none, and refuses before rendering where it contradicts the sibling's. The owner opts in later and moves files with `make files-plan`. `adopt.sh` also names any file at a path where a data-root ignore file would land, and, where the repository keeps Drive workflows, tells the owner to answer `DATA_PROVIDER=google-drive` with `DATA_STORE=repo` (D37, D53). `adopt/` holds anonymised example answers files only.

## 9. Coexistence rules (for `syntek-media` and any later template)

1. Each template sets its own `_answers_file`.
2. Each template's instructions live in `.claude/rules/<template>/`; no template updates `.claude/CLAUDE.md`.
3. Shared root files are seed-if-missing (D17); agent entrypoints and client settings are copy-only (D47) and byte-identical across the family (D48), and the MCP servers they declare (D54) reach an existing project only through D52's script, once, whichever template's update runs first, where that template ships D52's script; each template ships its own `.claude/<template>-agents.md` bridge, its own `.claude/<template>-permissions.py` (the same bytes, D49), its own `.claude/<template>-dataroot.py` (the same bytes, D50) and its own data-root map `.claude/<template>-dataroot.json` (its own filing folders, D50), and every entrypoint reads every bridge present; each template's rules 06 carries the same text between the D48 `rules-web-tools` markers, under a heading it numbers itself.
4. Skill and layer names never collide, and the shared writing skills ship only from `syntek-author`, **except** the D51 shared working-practice files (`grill-me`, `grill-with-docs`, `grilling`, `handoff`, `wait-what`, `wayfinder` and `to-questionnaire` `SKILL.md`, both hooks with the `.claude/hooks/` pair, and the `handoffs/` pair), which every family template ships copy-only and byte-identical from `syntek-author`'s sources. Their mode files carry distinct names per template (this template's `THEOLOGY.md`, `FICTION.md`, `BUSINESS.md`; `syntek-media`'s `MEDIA-<KIND>.md`), so no mode file is owned by two templates, and each template's mode files apply only to its own work. Each template's update report (D52) attributes a file holding the sibling's version to the sibling, and each template's refs live under its own `refs/<template>/`.
5. Large binaries never sit in plain Git: generated audio and renders are git-ignored. Under `DATA_STORE` external, binary records and issued copies live under the one data root each machine names in `SYNTEK_DATA_ROOT`, at `<root>/<area>/<kind>/<slug>/<repo-relative path>`, listed with their sha256 in `external.toml`, whose format every family template shares (D50). Under `DATA_STORE` repo, issued documents and what D37's Drive pull brings in stay in Git, as before D50; the external store is the way out. No `lfs` store value in this release; a sibling's own LFS use (`syntek-media`'s large brand exports, its D19) is its own.
6. One project, one data-root layout: every template applied to a project records the same `DATA_STORE`, `DATA_AREA`, `DATA_SLUG` and kind folders. A template's first data-root answers default to the sibling's recorded ones and must equal them (`_external_data.peer`), and a sibling record without a store, from before D50, makes the first store default to `repo`; a later difference is reported after the update, and each template's resolver refuses its data commands while two records that both hold a store disagree, and only warns on a record without one (D50). `DATA_PROVIDER` defaults to the sibling's answer but is never refused: a difference is reported (D53). The peer key reads one sibling's answers file, so a third family template needs one `_external_data` key per sibling (accepted for this release).

## 10. Hazards

Never template: author identity or health data; income; clients, prices, invoices, credentials; testimony or named individuals; student numbers; the academic archive; absolute paths; source-repository names; project state written into skills. Ship empty: seeds, `refs`, registers. Fix rather than copy: AT's `appearances` table, conflicting confidence vocabularies, BD's conflicting disclaimers, BD's "we" against "I" (answered by `BUSINESS_VOICE_PERSON`), SC's builds that include `drafts/`, AT's `proposal.md` SCOPE concatenation bug, stale first lines naming another repository.

Client and tool hazards (D47):

- OpenCode: a committed `providers.<id>` replaces the `baseURL` of every model a collaborator has under the same id.
- Codex on Linux: `.agents` must not be a link (the bubblewrap sandbox fails).
- Copier: an empty user `settings.yml` crashes 9.17.1, and a settings value outside a question's choices fails every copy, even where the question is hidden.
- Gemini CLI: folder trust is on by default.
- Gemini CLI 1.0 removes `tools.exclude`; re-map `AskUserQuestion` (the permissions script, D49) when it lands.
- Copier: a user `settings.yml` default for `AGENT_CLIENTS` replaces the question's default outright: the none of the update that first asks it, and the recorded answer on a copy over a project made without `-a`; either way it can record clients whose files the project never received.
- Copier: a copy over a project whose answers file predates `AGENT_CLIENTS` defaults it to none; pass `--data 'AGENT_CLIENTS=[…]'` there.
- Copier: an `.agents` link that resolves outside the project fails every copy and update before `_exclude` is read. Updates hold it aside (D48), but `copier update --pretend` still refuses such a project, because a pretend run skips migrations; and an update that stops between the stages (a refused answer, Ctrl-C at a question, or Copier failing as it cleans up after the render) leaves the link held as `.agents.syntek-held`, so the next update refuses the dirty tree until the printed hand fix restores it; where Copier had already put `.agents` back, a bare `mv .agents.syntek-held .agents` would move the held link into the folder outside the project, so the fix removes that link first (`rm`, never `rm -r`).

Shared working-practice files and the update report (D51, D52):

- An owner-edited shared skill or hook is frozen and reported on each update that changes it, never three-way merged; tailor a project in a mode file, the rules or `.claude/CLAUDE.md`.
- Claude Code runs a personal skill (`~/.claude/skills/<name>`) in place of a project skill of the same name, and a `Skill(<name>)` deny or `skillOverrides` entry matches the name whatever its source. An author's personal `handoff`, `grill-me`, `grilling`, `grill-with-docs`, `wait-what`, `wayfinder` or `to-questionnaire` therefore replaces the shared one in the project, for the hooks too, and the refresh cannot reach it. This repository's development deny list also blocks a maintainer's personal skill that has any template skill's name. `README.md` says so.
- A shared file the owner deleted comes back when a sibling template is copied later (an ordinary copy writes a missing file).
- A shared file holding a sibling's revision, older or newer, is kept and reported until that template's own update refreshes it (D51); nothing downgrades.
- Never remove a shared file's two `copier.yml` lines once released: dropping the update exclusion makes the next update delete it, the sibling's copy included. Never write a folder-level skip or exclusion for a skill folder: it would freeze the template-owned mode files.
- A hook shipped at a mode other than 755 in either template makes a later copy conflict, because Copier compares the executable bit.
- `copier update --pretend` runs no migration, so no refresh and no report (`--skip-tasks` skips only the copy-time record, not migrations, in 9.17.1); Copier skips every migration when it cannot read a template version on either side (a source that is not a git repository, or no `_commit`); an untagged template still reports; `_message_after_update` says what to look for when no report appears.
- Copier deletes an owner-edited file the new version retires, and rej-mode conflicts drop the owner's lines into a `.rej` file, before any after-stage script runs: the report gives the restore command, it cannot prevent the loss.
- `git push --mirror`, a `+refs/*:refs/*` push, `git clone --mirror` and `git bundle create --all` carry `refs/<template>/template` and `refs/<template>/yours`. A plain push, `--all`, `--tags` and an ordinary clone or fetch do not. No namespace under `refs/` escapes a mirror push, and `git gc` does not keep a root ref outside `refs/`, so the records stay under `refs/<template>/`. `<template>/template` holds the template rendered with the owner's answers (no answers file, no absolute path) and the report. `<template>/yours` holds the owner's `HEAD` at the last update, so it keeps that commit reachable after an amend or rebase: a file since removed from history (a credential, say) stays in the clone, and a mirror push publishes it. Before rewriting history to remove a secret, delete both refs (`git update-ref -d`); the next update records them again. To mirror without them, set `remote.<name>.push` to `+refs/*:refs/*`, add `^refs/<template>/*`, then run `git push --prune <name>` (`--mirror` takes no refspec). `_message_after_update` and `README.md` say so.
- A render without a record (a fresh clone, a `--skip-tasks` copy, a project older than D52) re-renders the old version under today's Copier; an answers file older than D47 lacks `AGENT_CLIENTS`, so that render passes `AGENT_CLIENTS=[]`.
- An update in which Copier's own cleanup failed (`OSError: [Errno 39] Directory not empty` under the `.git/objects` of a temporary `copier._main.old_copy.…` or `copier._main.new_copy.…` folder) ran no after-stage migration, update report or message after the update, though its answers file already records the new version, so an update run over that state skips the release's migrations. The cause is Git's automatic maintenance, which a commit in Copier's own temporary render starts in the background and which may still be writing when Copier deletes the folder (intermittent; more likely with a recent Git and with several updates at once); it is Copier's to fix. `README.md` 'Updating a project' and the bridge give the update command with `gc.auto` and `maintenance.auto` off for that run, and the recovery: discard the stopped update and run it again. The script's own renders, and every Git the audits start, set both off.
- Not verified: Windows (quoting, `core.symlinks=false`, CRLF), pipx, and a remote `gh:` source for the script's own render.

Data root (D50):

- An empty `SYNTEK_DATA_ROOT =` in an included makefile (`tooling/project.mk`) blocks the environment variable; the seed never assigns it. A Claude Code hook never sees a value set only on the `make` command line, so the guard also finds a root by its marker.
- An unmounted volume's mount point is an empty folder: the owner-made marker is the check, and the resolver never creates it.
- On macOS, Linux and WSL Claude Code leaves `Grep` and `Glob` out of its default tools and searches with `find` and `grep` through Bash, which the guard does not parse: there the guard stops edits and writes under a data root, and only the rules keep a search out of it. Other clients get no guard at all.
- A case-insensitive disk (NTFS, SMB, default APFS) treats `Business/` and `business/` as one folder and a Linux disk as two, and NFC and NFD spellings of one name differ on a shared volume; the resolver warns, and refuses to create the second spelling.
- NTFS and SMB refuse `:` and the other reserved characters, device names and a trailing dot or space in any path component, and limit path length; `check-names` runs on every `add`, and an NTFS-3G mount wants `windows_names` (not verified).
- Copier's temporary renders never see the peer file, so no peer validator fires there; a fresh copy prints two MissingFileWarning lines; a sibling's answers file left behind after the sibling is removed still constrains this template's first data-root answers. Remove a template's answers file with the template.
- A user `settings.yml` value for `DATA_STORE` that a template does not offer (a later `lfs`) fails every copy of that template, even where hidden: the family adds a value in one release.
- A user `settings.yml` default for any data-root key replaces its whole default expression: Copier takes it before the question's own `default:`. For `DATA_STORE` it replaces both the sibling's record and `repo` on the update that first asks it: with `--defaults` every existing project's first update records it, and under `external` a business Drive project loses `.github/`, edits included. A settings `DATA_SLUG` gives every project the same folder, and a settings area or kind that differs from a sibling's recorded answer fails the first answer. A validator cannot tell a settings value from `--data`, so the README and `_message_before_update` say never to set `DATA_STORE` or `DATA_SLUG` there, and an area or kind only where it equals every sibling's recorded answer.
- `git check-ignore` errors on a path outside the work tree: no scan is given a path under the data root.
- An owner's own file at a data-root ignore path comes back with conflict markers (exit 0, `UU`) on the update that opts in to `external`; the report lists it under CONFLICT.
- Untracking binaries deletes them from every other clone's work tree when it pulls that commit: verify the root on every machine first. Switching back to `repo` deletes the ignore files and brings no file back, and Copier forgets the area, slug and kind answers it then hides: a later return to `external` re-derives them from the sibling or the defaults, so note them first and pass them again with `--data`. Each manifest row's `filed_under` lets the resolver find the files and name the old folders.
- A copy from a local path (`--vcs-ref=HEAD`) records an absolute `_src_path` in the tracked answers file: generate real projects from `gh:`.
- Never put the repository inside a synced folder (a sync service copies file by file and corrupts it: Git's FAQ), or the data root inside the repository: the resolver refuses a root and a repository that contain one another, or a marker above the repository (every data command but `status`, which warns, exits 2), and every command but `guard` warns where the repository sits under a known sync folder (D53); it cannot see rclone, Syncthing or a share.

Data-root providers and the Drive workflows (D53, D37):

- Copier: during an update the old version renders with the new `_exclude` against the old answers, so a bare test of a new question on a path an earlier release shipped drops that path from the merge base. Every changed or owner-edited file then conflicts, and a gate closing in that update leaves the files unmanaged. Gates default each new key (Section 3.5).
- Copier: a user `settings.yml` default for `DATA_PROVIDER` replaces the mapping from a recorded `INCLUDE_DRIVE_SYNC`. With `--defaults`, the crossing update deletes a live project's Drive workflows. A scripted `--data INCLUDE_DRIVE_SYNC=…` is accepted and ignored.
- A fresh business copy beside a sibling that records `DATA_STORE: repo` and `DATA_PROVIDER: google-drive` inherits both. Under `--defaults` it ships the Drive workflows unasked, and they fail until their secrets exist.
- A business project with the Drive workflows, beside a sibling whose record already holds `DATA_STORE: external` (the owner answered it there), defaults to `external` on the update that first asks the store and cannot answer `repo` there (D50's first-answer rule), so that update deletes `.github/`, edits included; D52's report lists them (inferred, not probed together). A sibling whose record holds no store, from before D50, gives `repo` instead and keeps them.
- Drive workflows the template does not manage still run: a project's own, or ones restored after an answer deleted them. The commit that untracks binaries for the external store then bins every Drive copy. The v0.5.0 report migration lists them, and the pre-v0.5.0 ones the crossing update deleted (the update report offers to restore any the owner had edited); the template's own copies from v0.5.0 stop under any store but `repo`. One restored after that update is listed only by running the migration again.
- Reading an online-only file downloads it, and antivirus and indexers can do the same. `verify` never reads one without `--hydrate`.
- Not verified: the store guard on GitHub Actions; that `stat` never downloads a placeholder; the OneDrive and Google Drive conflict-copy names; the completeness of the sync-folder list.

Shipped MCP servers (D54):

- **Stealth by design.** Scrapling's stealth tools are built to look like a person's browser and to get through anti-bot protection. `real_chrome` drives the installed Chrome with a fresh profile; `cdp_url` attaches to any browser that exposes DevTools at the address given, on this machine or another, in a new context that shares none of its cookies, and the requests then leave from that browser's address; `executable_path` launches whatever program it names. `make_request` and `bulk_get` impersonate Chrome's TLS fingerprint and are, by decision, not asked. No tool reads `robots.txt` or limits its rate, and the bulk tools fetch up to 50 pages at once. `screenshot`, also unasked, loads any URL in a session already open. Rules 06 Section 13 governs their use, and the asks are the only gate in Claude Code.
- **The plain tools write and reach local services.** `make_request` and `session_make_request` take any method (POST, PUT, DELETE) with a form or JSON body, `follow_redirects` and `verify`; the default `follow_redirects='safe'` refuses only a redirect to a private address, never a URL the call names (loopback, the LAN, link-local cloud metadata, a DevTools port). All three plain tools are marked read-only, so Codex runs them without asking, and they run in the MCP server, outside Codex's shell sandbox and its network block. Rules 06 Section 13 limits them to a GET with no body to a public address unless the author agrees. With a `file://` URL they, and the browser tools, read local files: `curl_cffi`'s libcurl and Chromium accept the scheme, and nothing in Scrapling checks it.
- **Approval differs by client.** Claude Code evaluates deny, then ask, then allow, and the first match decides whatever its specificity: an added ask overrides an owner's `mcp__S__*` allow, which is why D51 reports rather than adds it. OpenCode lets the last match win, so its asks precede its denies. Codex runs a tool its server marks read-only without asking, so its prompt tables are load-bearing: an owner who deletes one loses that prompt, and `--check` reports it.
- **Start-up without approval.** OpenCode, and possibly Antigravity, start project servers when they open the project (no trust step is documented; unverified). The first start then downloads about 100 MB through uv and runs pinned third-party code whose dependencies are not pinned. An interactive Claude Code session asks first; `claude -p` and the Agent SDK connect a project's `.mcp.json` servers without asking, approved or not, unless the run passes `--setting-sources user` or `--bare`, or a `disabledMcpjsonServers` entry rejects the server (<https://code.claude.com/docs/en/permissions>, 'What runs before you trust a folder'). Codex and Gemini CLI need trust.
- **First-start timeouts.** A cold first start can exceed a client's start-up timeout: Claude Code's documented 30 seconds, and Codex's server-dependent default. The bridge's warm-up commands avoid it; the browser is fetched only by the download command the author runs, `playwright install chromium`. `scrapling install` must not be used: it also runs Playwright's `install-deps`, which raises privileges through `sudo`, or `su root` where `sudo` is absent.
- **code-review-graph reaches past the project.** Every tool honours a caller's `repo_root`, checked only for a `.git`, `.svn` or `.code-review-graph` entry, and then builds or reads that repository's graph; `list_repos_tool` and `cross_repo_search_tool` search every repository in `~/.code-review-graph/registry.json`, and building a graph creates `~/.code-review-graph/`. The per-call prompt Claude Code, Codex and Gemini CLI give these unannotated tools is the gate, until an owner allows the server broadly; OpenCode's own default allows every tool the project does not ask for, so there the rules are the only gate; rules 06 Section 13 tells a session to do neither without the author's word. While Git tracks nothing (a new project before its first `git add`) it walks every file on disk, ignoring `.gitignore`.
- **Approval in OpenCode follows the file's order.** OpenCode lets the last matching rule win, so an owner's earlier broad allow would cover a server added after it: D52's script adds a server to `opencode.json` or `.gemini/settings.json` only once that file holds the server's asks.
- **The tool list is unvalidated.** code-review-graph ignores an unknown `--tools` name, drops a tool whose name is misspelt, and exposes all 30 tools, `embed_graph_tool` included, when the list is empty. `family-shared.sh` holds the list.
- **`code-review-graph install`, `init` and `uninstall`** add an unpinned entry offering all 30 tools, cloud keys inherited, to `opencode.json` and to the Codex and Antigravity files in the home folder (they keep the pinned, keyless entries in `.mcp.json` and `.gemini/settings.json` as hand-written, and add one only where the owner removed it), inject text into `AGENTS.md`, `GEMINI.md` and `CLAUDE.md`, add or remove skills, hooks and a git pre-commit hook, write user configuration, and append an unanchored `.code-review-graph/` to the root `.gitignore`. Never run them. Its `graph.db` holds absolute paths and is never committed: the tool's own `*` ignore file covers projects made before the seed line.
- **Offer-once never delivers a pin bump.** A security fix in a later Scrapling or code-review-graph reaches an existing project by hand until a release refreshes unedited entries by their recorded hash. A deleted `.mcp.json` comes back, holding both servers, because Copier recreates a missing seed.
