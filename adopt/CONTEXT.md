# CONTEXT.md — adopt/

The tools for bringing an **existing** writing repository under the template.
There is no `copier adopt`: adoption is a `copier copy` into the repository, and a copy can write and replace files but never move them.
It comes in two modes. **Moving** adoption (`copier copy --overwrite`) lets the template take over its own paths, so this folder does the moving first.
**Additive** adoption (`copier copy --skip '*' --skip-tasks`, DESIGN.md D41) keeps every existing file exactly as it is and adds the template beside it, so this folder reports what the copy will add and keep and what to extend by hand.
It also supplies example answers for the copy.
It holds no real project's answers, names or paths: the example values are invented, and an author's real answers file stays outside this repository.

## Directory Tree

```text
adopt/

├── CLAUDE.md             ← operating rules for changing the scripts

├── theology.sh           ← adopt.sh --kind theology (DESIGN.md Section 8 names one per kind)
├── fiction.sh            ← adopt.sh --kind fiction
├── business.sh           ← adopt.sh --kind business
└── examples/

    ├── fiction.answers.yml    ← invented answers for a novel with both fiction kits
    └── business.answers.yml   ← invented answers for a business library
```

## What's here

- `adopt.sh` (moving adoption, the default) — **advisory by default**: it prints what it would do and changes nothing. With `--apply`, on a branch other than `main` or `master` in a git work tree, it performs only the moves DESIGN.md Section 8 lists, each of which has exactly one correct destination: `workspace/{handoffs,learning,maps}` out of `workspace/`, `voice-and-tone.md` to `voice-notes.md`, stub chapter files to `planning/src/units/`, flat `docs/*.md` guides to `docs/project/`, bespoke workflows to `workflows/local/`, `status: stub` to `outlined`, and the section sign to 'Section' in governance Markdown. **It never overwrites and never deletes**; an existing destination is reported as a collision. A second run is a no-op. It also names `how-to` that is not a folder (and `--apply` then refuses), the repository's files at the user guide's paths, and its other files under `how-to/` (DESIGN.md D56).
- For business it also reports every `library/src/` folder that is not one of the document families (DESIGN.md D39), with the family the template files its documents in. Which family a folder belongs to is the author's call, so it is never moved.
- `adopt.sh --additive` (additive adoption) — **report only, never `--apply`**. It renders the template for the kind into a temporary folder (with the answers file named by `--answers`, or the defaults) and compares that tree with the repository. It names:
  - **the source and ref it previewed** (this clone at HEAD, its tag if it has one, and whether it is dirty); its closing step copies from exactly that, because a report on one tree is not exact for another;
  - what the copy will **add** (per folder) and **keep** (every file at a template path), each kept file marked **kept, committed**, **kept, staged**, **kept, untracked** or **kept, ignored**: a file an earlier copy left and nobody committed is the template's, not the repository's, so it is removed before the copy rather than kept as the repository's own;
  - every **same-named** file: one the copy adds beside the repository's own file of that name in a neighbouring folder of the same tree (its parent, a sibling or a child), such as the template's `library/docs/reference/X-standards.md` beside the repository's `library/docs/X-standards.md`, with the `## Overrides` redirect line `` `<template path>` → `<project path>` `` that points every template file at the repository's copy (D40);
  - every template path the repository's ignore rules hide, from `git check-ignore`, marked **ignored** with its `source:line:pattern`. Git never commits such a file, and the next `copier update` deletes it, or replaces a kept file of the repository's own there. The moving mode's unanchored `build/` advice runs here too;
  - every kept file at a family's or an option's template path, read from `copier.yml`'s `_exclude` gates: unticking that family or turning that option off later deletes it, so it must be copied out first;
  - every kept `.claude/skills/<name>/SKILL.md` beside which the template writes a mode file, marked **inert**, because a mode file applies only when its `SKILL.md` carries the Mode paragraph; and every kept `SKILL.md` at a shared working-practice path (read from `migrations/family-refresh.json`, DESIGN.md D51), which no update merges or replaces and each update report lists when the template changes that skill;
  - every kept `CONTEXT.md` whose folder gains template entries it does not name, to **extend** by hand, and every kept `workflows/CONTEXT.md` without the 'You want to… | Procedure' table;
  - every template `CONTEXT.md`, `CLAUDE.md` or `README.md` added to a folder that already holds the repository's own files, to check against its layout and record in `00-project.md` `## Overrides`;
  - two procedures that will share a workflow number in one layer;
  - for business, a kept `google-drive-*.yml` workflow (in the `DATA_PROVIDER` wording, D53), and a kept workflow that mentions `library/src/` and would sync the `drafts/` folders the copy adds (D37);
  - the data root and the MCP servers, as both modes report them (below);
  - the settings files the copy writes, `.claude/rules/syntek-author/00-project.md` and `tooling/project.mk`, with the build settings a repository usually needs there: its logo folder, its own open-item marks, its Word converter;
  - a kept `Makefile` that differs from the template's, whose targets (the D42 filter, the D43 issue guard) are then not installed.

  Its closing steps also say that `--skip-tasks` skips the copy-time task that records the template's render for the update report (DESIGN.md D41, D52), so the first `copier update` renders the old version itself, once, to build its report.

  Run it before the copy to preview, and after it to see what is left to extend. The repository is never written to.
- The moving report also names what the copy will **keep** (seeds that already exist, read from `copier.yml`'s `_skip_if_exists` at run time so the list cannot drift, and what each lacks against the template's seed, such as a `.gitignore` whose unanchored `build/` line would hide `.claude/skills/build/`) and what it will **replace** (files at template paths, when run from a clone that holds `template/`), plus everything only the author can decide: drafted chapters whose brief must be split out by hand, a workflow that is a template workflow under an older number, agents, a two-level manuscript, stray root files.
- Both modes report **the data root** (DESIGN.md Section 8, D50). A fresh copy keeps binary files outside the repository (`DATA_STORE` external), but an adopted repository usually tracks its scans, figures and issued copies, so every copy command they print passes `--data DATA_STORE=repo` and the files stay in Git until the owner opts in on a later update (then `make files-plan` lists what to file). The exception is a sibling: where another syntek template's answers file (`.copier-answers.syntek-*.yml`) already records a store, the copy must take that one, so the command passes none and the report says '`<file>` records DATA_STORE `<value>`'. The additive preview copies every such file into its folder before it renders, so it meets the same peer rule as the copy, and it renders into a folder of the repository's own name, which `DATA_SLUG`'s default reads. An `--answers` file that records `DATA_STORE` is the copy's own answer (a `--data` option would override it), so the command then passes none; one that contradicts the sibling's store stops the report with exit `2`.
- The data-root section also names:
  - every file of the repository's own where a data-root ignore file would land, read from `copier.yml`'s `_exclude` lines gated on the external store. Under repo the copy leaves it alone, and a later switch to external brings the template's back with conflict markers. Under a sibling's external, the moving copy replaces it, and the additive copy keeps it without the template's rules;
  - a kept `.claude/settings.json` without the data-root guard, which no copy or update adds.
- Both modes report **the MCP servers** (D54), read from `migrations/family-refresh.json`'s `mcp` key: a kept `.mcp.json`, and a kept client file the answers name, gains them once each, into its own text, from the moving copy or from the first update after an additive one. A git-ignored one is never read, so the report names the servers to add by hand.
- For business, a kept `google-drive-*.yml` workflow is reported in the `DATA_PROVIDER` wording (D53): the template ships its Drive workflows only with `DATA_PROVIDER` google-drive and `DATA_STORE` repo.
- Both modes check `.agents` (DESIGN.md D47). The template's `.agents/` is a real folder holding a `skills` link to `../.claude/skills` and `mcp_config.json`, both copy-only, so an existing `.agents/` of that shape (a companion template's, such as syntek-media 0.4.2's) is skipped and needs nothing. Where Copier would fail instead, the printed copy command carries the exclusion and the report says what to do by hand: `--exclude /.agents/skills` when `.agents/skills` is a real folder or a file, and `--exclude /.agents` when `.agents` is a link or a file, with the steps to replace the retired `.agents -> .claude` link by the real folder before the copy. It also reports a `skills` link to another target. Nothing there is ever moved or removed.
- `theology.sh`, `fiction.sh`, `business.sh` — the same script with `--kind` filled in.
- `examples/*.answers.yml` — the shape of a `--data-file` for `copier copy`: every question shown for that variant, with made-up values (business includes `BUSINESS_FAMILIES`). Each shows one `OPENCODE_PROVIDER` shape: theology `user`, fiction `named`, business a local Ollama server. Each answers `DATA_STORE: repo`, with a comment to delete it where a sibling's answers file records a store, and `DATA_PROVIDER: none`. Copy one outside the repository being adopted and change every value.
- Exit codes: `0` report printed (and safe moves made); `1` one or more `--apply` moves failed and were left in place; `2` usage error, `--apply` refused, or `--additive` could not render the template.

## Which mode

- **Moving** when the repository is young, or already close to the template's layout, and the template should own its governance from now on.
- **Additive** when the repository has conventions of its own that work — its own skills, a project `CLAUDE.md`, workflows numbered in its own series, a Drive or issuing practice — or holds confidential material nobody should reorganise. The template then reads where things live from `00-project.md`. **Two costs (D41):** the project's own files at template paths count as template files to Copier, so unticking a family or turning an option off deletes them; and a kept file the template later changes comes back with conflict markers on update (keep the project's version). A kept file at a shared working-practice path is the exception to the second: it is never merged, only listed in the update report. A kept `.claude/settings.json` gains only the hook entries and deny and ask rules the template lists, and `"autoCompactEnabled": false` and `"idleCompaction": false` where each key is absent (a value the owner set is kept and reported), add-only and into its own text: from the moving copy, or from the first update after an additive one (D51). A kept `.mcp.json`, and a kept client file the answers name, gains the two MCP servers the same way (D54). Either mode keeps the repository's binaries in Git (`DATA_STORE` repo) unless a sibling template's answers file records a store (D50). And `--skip-tasks` skips the copy-time record, so the first update's report renders the old version itself (D52); a moving adoption runs that task.
