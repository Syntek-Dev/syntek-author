# syntek-author

**A Copier template that generates writing repositories — a theology book, a novel or a business document library — with their own folder system, standards and a Claude Code skill suite.**

![Version](https://img.shields.io/badge/version-0.8.0-blue)
[![Licence: MIT](https://img.shields.io/badge/licence-MIT-green)](LICENSE)
![Template: Copier](https://img.shields.io/badge/template-copier-blue)

```bash
uvx --python '>=3.14' copier copy --trust gh:Syntek-Dev/syntek-author my-book
```

Copier asks its questions, renders the tree for the variant you choose, runs `git init`, and (for a project with references) builds the citation database.
How many questions it asks depends on your answers: the fiction kits only appear for a novel, the business settings only for a library.
New here? Start with [the user guide](template/how-to/src/TEMPLATE-GUIDE/syntek-author/01-overview.md), the same chapters every project carries in `how-to/`.

## What it generates

One template, three variants: a Christian non-fiction book (`theology`), a novel (`fiction`) or a library of business, legal and client documents (`business`), chosen once with `DOC_TYPE`. Every variant shares the same spine: an authoring loop in which the AI drafts one small section or proposes changes to yours and only your word moves a section into the work; a ledger that records who wrote what; reviews against numbered gates; production layers with guides and procedures; Claude Code skills, rules and hooks, read by other coding agents through a bridge; binary files kept outside Git under a data root; and two pinned, keyless MCP servers. Every project also carries its user guide, `how-to/`, which is read-only: every update puts it back. [What a project is](template/how-to/src/TEMPLATE-GUIDE/syntek-author/01-overview.md) · [what you receive, and what an update does to each kind of file](template/how-to/src/TEMPLATE-GUIDE/syntek-author/05-what-gets-generated.md).

Options add to a variant:

| Option                      | Offered for                | Default                                                                             | Adds                                                                                                                                                                                                                                                                                                             |
| --------------------------- | -------------------------- | ----------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INCLUDE_PROPOSAL`          | books                      | on                                                                                  | `proposal/`: the book proposal and endorsements (theology), or the query package and submissions tracker (fiction)                                                                                                                                                                                               |
| `INCLUDE_REFERENCES`        | all                        | theology only                                                                       | A SQLite references database → CSL-JSON → Pandoc in Harvard style, and the `add-reference` skill                                                                                                                                                                                                                 |
| `INCLUDE_SENSITIVE_CONTENT` | books                      | off                                                                                 | The sensitive-content standard, the `sensitivity-pass` skill and safe handling for testimony                                                                                                                                                                                                                     |
| `INCLUDE_WORLDBUILDING`     | fiction                    | on for fantasy and science fiction                                                  | Creatures, cultures and quests                                                                                                                                                                                                                                                                                   |
| `INCLUDE_CONLANG`           | fiction with worldbuilding | on with worldbuilding                                                               | Constructed languages: phonology, grammar, lexicon, etymology, a writing system and pronunciation                                                                                                                                                                                                                |
| `DATA_STORE`                | all                        | `external` on a new project; `repo` on an existing project's first update to v0.5.0 | `external`: three nested `.gitignore` files (`library/src/`, `research/src/`, `proposal/src/`) keep binary files out of Git, and you file them under each machine's data root instead (see [the data root](template/how-to/src/TEMPLATE-GUIDE/the-data-root.md)); `repo` keeps them in the repository, as before |
| `DATA_PROVIDER`             | all                        | `none`                                                                              | Which service keeps a copy of the data root; it only tailors the data-root checks, except in business with `google-drive` and `DATA_STORE` repo: GitHub workflows that push the library to Google Drive and pull it back (see [the data root](template/how-to/src/TEMPLATE-GUIDE/the-data-root.md))              |
| `BUSINESS_FAMILIES`         | business                   | every family but `msp-scp`                                                          | One document family per choice: its folder in `library/src/` (with `templates/`, client folders and `drafts/`), its standard in `library/docs/reference/`, its `<family>-documents` skill and its create workflow. `business` is always included                                                                 |
| `SEED_EXAMPLES`             | all                        | on                                                                                  | One worked example unit (and, with the constructed-language kit, a tiny example language)                                                                                                                                                                                                                        |

## Generating a project

From the published template:

```bash
uvx --python '>=3.14' copier copy --trust gh:Syntek-Dev/syntek-author my-book
```

From a local clone, rendering the checkout you have rather than the latest release tag:

```bash
uvx --python '>=3.14' copier copy --trust --vcs-ref=HEAD "$(realpath ../syntek-author)" my-book
```

The template path must be absolute, as `"$(realpath ../syntek-author)"` makes it, because Copier records it in the answers file and every later update reads the template from there; a relative path makes every update fail with 'Updating is only supported in git-tracked templates'.
A project rendered from `HEAD` must also be updated with `--vcs-ref=HEAD` (still with `-a .copier-answers.syntek-author.yml`) until a newer release tag exists, because Copier refuses to move it back to the older tag.
That absolute path is then in the answers file you commit, so generate real projects from `gh:Syntek-Dev/syntek-author`, and keep a local clone for trying the template out.

**The `MissingFileWarning` is expected.** On a fresh copy, an adoption and (with Copier 9.18) every update, Copier may warn that `.copier-answers.syntek-author.yml` was not found, and that `.copier-answers.syntek-media.yml` was not found. Both are harmless. The template looks for your previous answers so that an update can refuse a changed `DOC_TYPE`, and for the other syntek template's answers so that both keep one data-root layout; on a first copy, or without that template, there are none.

**Why `--trust`.** After rendering, the template runs four small tasks: `git init` (only where no repository exists), `chmod +x` on the session hooks, `make init` to build the references database, and a record of the rendered template inside `.git` that the first update's report compares against (see [Updating a project](#updating-a-project)). Copier treats any task as an unsafe feature and refuses to run one without `--trust`. Every task is non-fatal: if `sqlite3` or `make` is missing, the project is still complete and you run `make init` later.

Without prompts, for scripts and CI, pass every answer that has no default and accept the rest:

```bash
uvx --python '>=3.14' copier copy --trust --defaults \
  --data DOC_TYPE=fiction \
  --data "PROJECT_NAME=The Salt Ferry" \
  --data "PROJECT_DESCRIPTION=A ferry pilot on a drowned coast must carry a stranger across the salt marsh before the spring tide." \
  --data "AUTHOR_NAME=Robin Example" \
  --data DATE=03/10/2026 \
  gh:Syntek-Dev/syntek-author the-salt-ferry
```

`DOC_TYPE` has no default on purpose: without it, `--defaults` stops with an error rather than quietly generating a theology book.

When generation finishes, open the project in Claude Code. The generated `README.md` and `CONTEXT.md` describe that project; `.claude/CLAUDE.md` holds its brief and points at the rules. A project that answered `DATA_STORE` external (the default) also prints the three steps that set up a machine's data root ([the data root](template/how-to/src/TEMPLATE-GUIDE/the-data-root.md)); text work needs none of them. The project's own user guide starts at `how-to/src/TEMPLATE-GUIDE/syntek-author/01-overview.md`.

## The questions

How many questions Copier asks depends on your answers. Each is explained, with its default and what it costs to change later, in [chapter 04](template/how-to/src/TEMPLATE-GUIDE/syntek-author/04-the-answers.md).

| Question                                                                                                   | What it decides                                                                                        |
| ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| `PROJECT_NAME`                                                                                             | The project's name: a working title, or a plain name such as 'Client Documents'.                       |
| `PROJECT_SLUG`                                                                                             | Its machine name, in lower-case words joined by hyphens.                                               |
| `DOC_TYPE`                                                                                                 | `theology`, `fiction` or `business`: the whole tree. It never changes later.                           |
| `PROJECT_DESCRIPTION`                                                                                      | The brief: the thesis, the premise or the library's purpose, in a full sentence.                       |
| `AUTHOR_NAME`                                                                                              | Your name exactly as printed.                                                                          |
| `AUTHOR_FIRST_NAME`                                                                                        | What the skills call you in chat.                                                                      |
| `AUDIENCE`                                                                                                 | Who the work is for; the `comprehension` skill reads as this reader.                                   |
| `READER_TEST`                                                                                              | One sentence naming the reader every page must work for.                                               |
| `WORKING_TITLE`                                                                                            | Books: the title a proof prints.                                                                       |
| `SUBTITLE`                                                                                                 | Books: the subtitle, if any.                                                                           |
| `BIBLE_TRANSLATION`                                                                                        | Theology: the translation you quote by default.                                                        |
| `FICTION_GENRE`                                                                                            | Fiction: the genre, which sets the worldbuilding default.                                              |
| `INCLUDE_WORLDBUILDING`                                                                                    | Fiction: creatures, cultures and quests.                                                               |
| `INCLUDE_CONLANG`                                                                                          | Fiction: constructed languages, a writing system and pronunciation.                                    |
| `TRADING_NAME`                                                                                             | Business: the name your documents print.                                                               |
| `JURISDICTION`                                                                                             | Business: the law your contracts and policies are written under.                                       |
| `CURRENCY`                                                                                                 | Business: the symbol your prices use.                                                                  |
| `BUSINESS_VOICE_PERSON`                                                                                    | Business: 'I' or 'we'.                                                                                 |
| `BUSINESS_FAMILIES`                                                                                        | Business: which document families the library holds.                                                   |
| `INCLUDE_PROPOSAL`                                                                                         | Books: the book proposal (theology) or the query package (fiction).                                    |
| `INCLUDE_REFERENCES`                                                                                       | The citation database and Harvard references.                                                          |
| `INCLUDE_SENSITIVE_CONTENT`                                                                                | Books: the sensitive-content standard and its checks.                                                  |
| `SEED_EXAMPLES`                                                                                            | One worked example, copied once.                                                                       |
| `MODEL_MECHANICAL`                                                                                         | The model for renames, ticks and builds; substantive work always uses Opus.                            |
| `AGENT_CLIENTS`                                                                                            | Which coding agents besides Claude Code get their files.                                               |
| `CODEX_MODEL` · `GEMINI_MODEL`                                                                             | Those clients' models.                                                                                 |
| `OPENCODE_PROVIDER` · `OPENCODE_BASE_URL` · `OPENCODE_MODEL` · `OPENCODE_CONTEXT`                          | OpenCode's model, and a local server if you run one.                                                   |
| `DATA_STORE`                                                                                               | Where binary files are kept: under a data root outside the repository (`external`), or in it (`repo`). |
| `DATA_AREA` · `DATA_SLUG` · `DATA_KIND_DOCS` · `DATA_KIND_PHOTOS` · `DATA_KIND_AUDIO` · `DATA_KIND_VIDEOS` | With `external`: the folders under the data root.                                                      |
| `DATA_PROVIDER`                                                                                            | Which service you run to keep a copy of the data root.                                                 |
| `TIMEZONE` · `DATE`                                                                                        | Your time zone, and the date in every header.                                                          |

Copier can also read your own defaults from a settings file. Never set `AGENT_CLIENTS`, `DATA_STORE` or `DATA_SLUG` there, and set `DATA_AREA`, a kind folder, a model or an OpenCode answer there only where it equals every other syntek template's recorded answer: chapter 04 says why.

Every project keeps its own settings in two files written once from your answers, `.claude/rules/syntek-author/00-project.md` and `tooling/project.mk` ([chapter 06](template/how-to/src/TEMPLATE-GUIDE/syntek-author/06-a-tour-of-the-project.md), [chapter 09](template/how-to/src/TEMPLATE-GUIDE/syntek-author/09-customising.md)).

A new project keeps its binary files (scans, signed and issued copies, large images, generated audio) outside the repository, under a data root you name on each machine with `SYNTEK_DATA_ROOT`; `DATA_STORE=repo` keeps them in the repository instead, and an existing project or an adoption starts there. Decide before you generate; [the data root](template/how-to/src/TEMPLATE-GUIDE/the-data-root.md) explains both. What `copier update` does to each kind of file: [chapter 05](template/how-to/src/TEMPLATE-GUIDE/syntek-author/05-what-gets-generated.md).

## Updating a project

Always on a branch, always with the answers file named, and with Git's automatic housekeeping off for the run:

```bash
git switch -c update-syntek-author
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx --python '>=3.14' copier update --trust -a .copier-answers.syntek-author.yml
git status && git diff     # review; resolve any conflict markers
git add -A && git commit -m 'Update from syntek-author'
```

**Why housekeeping off.** Copier renders the template into temporary Git repositories and commits in them, and after a commit Git may start its automatic maintenance in the background. If that is still writing when Copier deletes the temporary folder, the update stops with `OSError: [Errno 39] Directory not empty` on a `.git/objects` path under a `copier._main.old_copy.…` or `copier._main.new_copy.…` folder. It is intermittent, most likely with Git 2.54 or 2.55 (Git 2.56 starts the background repack only above about 7,000 loose objects) and with several updates running at once. The five variables in front of the command turn `gc.auto` and `maintenance.auto` off for that one command, in every Git it starts, and change none of your Git settings. The form is for POSIX shells such as bash and zsh, and needs Git 2.31 or later. Give every other update command in this README the same five variables in front.

**If an update stopped with that error,** Copier had already written the new version's files and recorded the new version in `.copier-answers.syntek-author.yml`, but nothing that runs after the render had run: no after-stage migration (the release's own report, such as v0.5.0's, included), no update report, no refresh of the shared files, no settings entry or MCP server added, no message after the update, and an `.agents` link outside the project is still held aside. Never commit that state: an update run over it takes the new version as already reached, so it reports '0.5.0 → 0.5.0' and skips that release's migrations. Discard it and run the update again, from the project root, in this order. First, if `.agents.syntek-held` exists, put the link back as 'An `.agents` link outside the project' below says: `git clean -fd` would delete it. Next run `git clean -n -d`, a dry run that deletes nothing: it lists every untracked file and folder the discard would delete, not only the update's (Copier refuses to start over untracked files only where Git shows them: with `status.showUntrackedFiles` set to `no`, it runs over yours), so commit or move out of the project anything of yours it lists; files Git ignores are left alone. `git reset --hard` discards every uncommitted change in the repository, so the project must be its own repository. Then:

```bash
git reset --hard && git clean -fd
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx --python '>=3.14' copier update --trust -a .copier-answers.syntek-author.yml
```

Where it stopped with `FileExistsError` or `NotADirectoryError` naming `how-to`, `how-to` is a file; where it stopped with `ForbiddenPathError` naming a path in `how-to`, `how-to` is a link that leads outside the project. Either way, after the discard and before the second run, give it another name and commit (`git mv how-to my-how-to` for one Git tracks), as [updating and recovery](template/how-to/src/TEMPLATE-GUIDE/updating-and-recovery.md#when-an-update-stops) says, or the second run stops the same way.

The second run reports from the version you had ('0.4.0 → 0.5.0', say), runs every migration the crossing calls for, and delivers what an update that never stopped delivers.

Discarding an update and running it again is safe; run template updates on one line of history, because the update's record is kept per clone, not per branch. Every update ends with a report of each file it did not deliver, with a command to compare and one to take the template's version, and it puts back the user guide's files in `how-to/`, which is read-only, listing each. The report's records live in `.git` under `refs/syntek-author/`: `git push --mirror` publishes them, and `syntek-author/yours` keeps your `HEAD` at the update reachable, so delete both with `git update-ref -d` before rewriting history to remove a secret. To mirror a repository without them, configure the remote instead of using `--mirror`: `git config remote.<name>.push '+refs/*:refs/*'`, `git config --add remote.<name>.push '^refs/syntek-author/*'`, then `git push --prune <name>`. A skill of the same name in your own `~/.claude/skills/` replaces the project's shared one, which no update then reaches. The answers file must be named with `-a` (`.copier-answers.syntek-author.yml`), and scripts add `--defaults`. Every step, the report's sections, changing an answer and the migrations are in [updating and recovery](template/how-to/src/TEMPLATE-GUIDE/updating-and-recovery.md), [chapter 04](template/how-to/src/TEMPLATE-GUIDE/syntek-author/04-the-answers.md) and [the update procedure](template/how-to/workflows/syntek-author/01-update-the-template/).

**An `.agents` link outside the project.** One pair of migration steps runs on every update and is keyed to no release (DESIGN.md D44, D48). Copier refuses to render anything beneath an `.agents` link that resolves outside the project, `--exclude` included, so where `.agents` is such a link (to an agent tree of your own beside the project, say), the update renames it to `.agents.syntek-held` before the render and back afterwards: the net change is zero, and its target is never followed, read or changed. Those steps run on the Python that runs Copier, which the command above asks to be 3.14 or later; on an older one they hold nothing and say so in a message framed in lines of `=`, and the update stops with `ForbiddenPathError` naming a path in `.agents`: discard it as above, then run the update again as shown. A real `.agents/` folder whose `skills` link points outside needs nothing. If an update stops before it ends (a refused answer, Ctrl-C at a question, or Copier failing as it cleans up after the render), the link stays held as `.agents.syntek-held`, and the next update refuses the changed tree, and `.agents` may stand again (the update or a discard can put it back). Put the link back from the project root, in a POSIX shell (Terminal on macOS and Linux, Git Bash on Windows; never PowerShell's `rm`), before anything else, and before discarding the stopped update with `git reset --hard` and `git clean -fd`, which would delete a held link Git does not track. First check what stands at `.agents`: `ls -ld .agents .agents.syntek-held`. Where it shows no `.agents.syntek-held`, nothing is held: stop here and change nothing. Where `.agents` is a link (its line shows `->`), remove that link alone with `rm .agents` (never `rm -r`, never a trailing slash); where it is a folder or a file, move it aside to a name nothing holds yet (`ls -ld .agents.from-update` finds nothing) with `mv .agents .agents.from-update` (no trailing slash), which holds what the update wrote (check it, and delete nothing in it that is yours). Then, once `ls -ld .agents` finds nothing, run `mv .agents.syntek-held .agents` (no trailing slash). Never run that `mv` while `.agents` stands: it would put the held link inside it, and inside the folder outside the project where `.agents` is a link. Then update again; where `git status` still shows changes (a stop after the render), discard the stopped update first: run `git clean -n -d`, a dry run, move out of the project anything of yours it lists, then `git reset --hard && git clean -fd`. Where the held link was committed beside an identical `.agents` link, the next update moves nothing, says so, and asks you to remove the held link (`rm .agents.syntek-held`), commit, and update again. `copier update --pretend` still refuses such a project, because a pretend run skips migrations. A copy runs no migration: see 'An existing `.agents` folder' below.

**Crossing a release that moved something.** The update runs that release's migration, which prints what it moved, what it left for you and every seed line to change by hand. What each release changed for existing projects is in [`CHANGELOG.md`](CHANGELOG.md).

Commit `.copier-answers.syntek-author.yml` and never edit it by hand; it is the record every future update merges against.

## Adopting an existing repository

There is no `copier adopt`. Adoption is a `copier copy` into the repository you already have, in one of two modes:

- **Moving adoption** (`copier copy --overwrite`): the template takes over its own paths, and the adoption script first moves your work into the template's layout. Choose it for a young repository, or one already close to the template's layout, whose governance the template should own from now on.
- **Additive adoption** (`copier copy --skip '*' --skip-tasks`): every file you have stays exactly as it is, nothing moves, and the template's files are added beside yours; `.claude/rules/syntek-author/00-project.md` then tells the template where your repository keeps things. Choose it for an established repository with conventions of its own that work — its own skills, a project `CLAUDE.md`, workflows numbered in its own series, a Drive or issuing practice — or one holding confidential material nobody should reorganise. **The caveat:** to Copier, a file you keep at a template path is a template file, so unticking a family or turning an option off on a later update deletes it, and a kept file the template later changes comes back with conflict markers (keep your version). Steps 5 and 6 below say how to meet both.

Either way, seeds you already have (`.claude/CLAUDE.md`, `MEMORY.md`, `settings.json`, `README.md` and the rest of class 2) are never overwritten, and `SEED_EXAMPLES=false` keeps an invented example out of a repository with real work in it.

Both modes also answer `DATA_STORE=repo` (DESIGN.md Section 8): an adopted repository usually holds tracked binaries, and they stay in the repository until you opt in to the data root and copy them out with `make files-plan`. Where another syntek template in the repository already records a store, leave `--data DATA_STORE=repo` out and drop `DATA_STORE` from the answers file: the copy then takes that template's store, and `adopt.sh` prints the command that way and says so. In the additive preview, an `--answers` file that records `DATA_STORE` (the examples' `repo` line, say) is the copy's own answer, so `adopt.sh` then prints the copy with no `--data DATA_STORE`, which would override it, and says so; where that store contradicts the one the other syntek template's answers file (`.copier-answers.syntek-media.yml`) records, it stops before rendering (exit `2`), because Copier would refuse the copy. `adopt.sh` also names a file of yours at a path where a data-root ignore file would land, and a kept Drive workflow, for which you answer `DATA_PROVIDER=google-drive` with `DATA_STORE=repo`. A kept `.mcp.json` gains the two MCP servers, once each, in its own text, from the moving copy or from the first update after an additive one; a git-ignored one is never read, and the report says so.

### Moving adoption

1. **In the repository you are adopting, make a branch.** Commit or stash anything outstanding, so `git diff` shows only the adoption.

   ```bash
   git switch -c adopt-syntek-author
   ```

2. **Run the advisory script** from a clone of this template. It reports what it would move and changes nothing:

   ```bash
   bash /path/to/syntek-author/adopt/theology.sh          # or fiction.sh, business.sh
   ```

   Then run it again with `--apply`. It performs only the moves that have exactly one correct destination — `workspace/handoffs` and `workspace/learning` to the root, `workspace/maps` to `planning/src/maps`, `voice-and-tone.md` to `voice-notes.md`, chapter files that are still stub briefs to `planning/src/units/`, flat `docs/*.md` guides to `docs/project/`, bespoke workflows to `workflows/local/`, `status: stub` to `outlined`, and the section sign to 'Section' in governance files — and reports everything else for you to decide, including (business) every folder under `library/src/` that is not one of the document families. It never overwrites and never deletes, and a second run is a no-op. Review and commit the moves.

3. **Copy the template over the repository**, with an answers file you have edited from `adopt/examples/`:

   ```bash
   cp /path/to/syntek-author/adopt/examples/theology.answers.yml /tmp/answers.yml   # then edit every value
   uvx --python '>=3.14' copier copy --trust --overwrite --data-file /tmp/answers.yml \
     --data SEED_EXAMPLES=false --data DATA_STORE=repo gh:Syntek-Dev/syntek-author .
   ```

   To adopt from a local clone instead, replace `gh:Syntek-Dev/syntek-author` with the clone's absolute path, such as `"$(realpath ../syntek-author)"`, and add `--vcs-ref=HEAD` (see [Generating a project](#generating-a-project)).
   `--overwrite` lets the copy replace the template's own files without stopping at each one.

4. **Review `git diff`.** Anything project-specific that a template file replaced — a paragraph in an old folder `CLAUDE.md`, a step in an old workflow — goes back into `docs/project/`, `workflows/local/` or `.claude/CLAUDE.md`. Because your seeds were kept, compare them with the template's: the adoption report names what a kept `settings.json`, `.claude/CLAUDE.md`, `MEMORY.md` or `.gitignore` lacks. In particular, a kept `.gitignore` with an unanchored `build/` (or `build`) line ignores every folder named `build`, including the `.claude/skills/build/` skill, which would then never be committed: change the line to `/build/`. Then fill in `.claude/rules/syntek-author/00-project.md`.

5. **Commit**, including `.copier-answers.syntek-author.yml`. From here, `copier update` works as above.

A manuscript laid out in two levels (sections holding chapters) is not supported in this release; the script reports it and moves nothing in it.

### Additive adoption

1. **Make a branch**, as above, from a clean tree. A file at a template path that git does not hold — left by an earlier attempt, say — is kept by the copy as if it were yours; the preview marks each kept file committed, untracked or ignored, so commit what is yours and remove the rest first.

2. **Preview the copy.** The script, with `--additive`, renders the template for your answers into a temporary folder, compares it with your repository and changes nothing:

   ```bash
   bash /path/to/syntek-author/adopt/business.sh --additive --answers /tmp/answers.yml
   ```

   It lists what the copy will add and what it will keep, and names three things to act on: a mode file (`THEOLOGY.md`, `FICTION.md` or `BUSINESS.md`) the template writes beside a `SKILL.md` you keep, which stays **inert** because a mode file applies only when its `SKILL.md` carries the Mode paragraph; each kept `CONTEXT.md` whose folder gains template entries it does not name, to **extend** by hand; and two procedures that will share a workflow number, to be cited by full folder name from then on. It also names every template path your ignore rules hide (with the rule that hides it), every file you keep that unticking a family or turning an option off would later delete, every template signpost added to a folder that already holds your own files, and a kept workflow that would sync the new `drafts/` folders. Every file it keeps is marked **kept, committed**, **kept, untracked** or **kept, ignored**. And it lists each **same-named** file: a template file the copy adds beside your own file of that name in a neighbouring folder, such as the template's `library/docs/reference/business-standards.md` beside your `library/docs/business-standards.md`, with the redirect line for `## Overrides` that makes every template file read yours. Its first line names the source and ref it previewed.

3. **Copy the template beside your files:**

   ```bash
   uvx --python '>=3.14' copier copy --trust --skip '*' --skip-tasks --data-file /tmp/answers.yml \
     --data SEED_EXAMPLES=false --data DATA_STORE=repo gh:Syntek-Dev/syntek-author .
   ```

   To adopt from a local clone instead, replace `gh:Syntek-Dev/syntek-author` with the clone's absolute path, such as `"$(realpath ../syntek-author)"`, and add `--vcs-ref=HEAD` (see [Generating a project](#generating-a-project)). Preview and copy from the same source and ref, or the report is not exact: the script previews its own checkout at `HEAD`, and its closing note prints the copy command for that source.
   `--skip '*'` keeps every file that already exists; `--skip-tasks` leaves your repository's set-up alone, so run `chmod +x .claude/hooks/*.sh` yourself (and `make init` if you use the references kit). It also skips recording the template's render for the update report, so your first `copier update` renders the old version itself, once, to build its report. `git status` shows only additions.

4. **Fill in `.claude/rules/syntek-author/00-project.md`:** `## Paths` (where your repository keeps each thing), `## Memory headings` (your `MEMORY.md` headings), `## Workflow aliases` (your procedure in place of a template one) and `## Overrides`, with a redirect bullet for each same-named file the preview listed. For business, set `BRAND_DIRS` in `tooling/project.mk` if your brand files live outside `standards/brand/`. Then run the script again and extend the index files it names.

5. **Know what a later update can delete.** In a repository adopted additively, a file of yours at an unticked family's or option's template path (its skill, its folder pairs) is deleted with it: copy it out first. Before you untick a family or turn an option off, check whether any file you kept sits at one of its paths.

6. **Commit**, including `.copier-answers.syntek-author.yml`. In a repository adopted additively, a file you kept at a template path comes back with conflict markers whenever the template changed it: keep your version, and extend it by hand if you want the template's change. A skill of your own at a shared skill's path (`handoff`, `wayfinder` and the rest of class 5) is never merged or replaced: the update report lists it whenever the template changes that skill.

What a project adopted either way should know afterwards: [chapter 11](template/how-to/src/TEMPLATE-GUIDE/syntek-author/11-adopting.md).

## A second template, other clients and the MCP servers

syntek-author can share a repository with a companion template such as syntek-media: each keeps its own answers file, rules folder, bridge and guide folder, the files both ship are shared byte for byte, and each is updated on its own, one at a time with a commit between ([chapter 10](template/how-to/src/TEMPLATE-GUIDE/syntek-author/10-a-second-template.md)). Combined projects need syntek-author v0.6.0 or later, updated first.

### Codex, Gemini CLI, Antigravity and OpenCode

Claude Code always ships, and `.claude/` is the one tree every client reads; `AGENT_CLIENTS` adds the others, each through a bridge file and settings written once ([agent clients and MCP servers](template/how-to/src/TEMPLATE-GUIDE/agent-clients-and-mcp.md), [adding a client later](template/how-to/workflows/syntek-author/03-enable-an-agent-client/)).

**An existing `.agents` folder.** A copy over an `.agents/` that already holds the same `skills` link and `mcp_config.json`, as a companion template writes them, needs nothing extra. Copier cannot write a link over a directory and fails before its skip check, so when `.agents/skills` is a real directory, copy with `--exclude /.agents/skills`; `adopt/adopt.sh` adds it for you. Never rename or remove the directory to make room: integrate its skills by hand. If `.agents` is itself a link (an older layout, such as a link to `.claude`), replace it with a real folder before you copy: updating syntek-media to 0.4.2 does this for its link, or replace it by hand. Until then `adopt/adopt.sh` prints the copy with `--exclude /.agents`. Otherwise the copy fails, with `--exclude /.agents/skills` it writes `.agents/mcp_config.json` through the link into `.claude/`, and Codex's sandbox fails on the link. If `.agents` is a link to a folder **outside** the project, Copier refuses everything beneath it even with `--exclude`, so move the link alone aside for the copy and put it back, from the project root: `mv .agents .agents.syntek-held`, copy with `--exclude /.agents`, then `mv .agents.syntek-held .agents` (run that last line too if the copy stops). `adopt/adopt.sh` prints the copy wrapped in those two lines, and never moves the link itself. The link's target is never touched; updates hold and restore it for you (see 'An `.agents` link outside the project' under [Updating a project](#updating-a-project)).

Every project ships two pinned, keyless MCP servers, Scrapling for web pages and code-review-graph for a local map of the project's code, with a prompt before each tool that drives a browser or writes files; the project's rules say how a session may use them, and the decision, and the responsibility, are yours. Pronunciation audio for constructed languages uses an ElevenLabs server you add yourself at user scope ([chapter 15](template/how-to/src/TEMPLATE-GUIDE/syntek-author/15-a-novel.md)).

Run one, or all of them before a commit:

```bash
bash .github/scripts/check-template-tokens.sh
bash .github/scripts/run-all.sh
```

`run-all.sh` renders every profile once and runs every self-test and every audit against those renders (`--no-self-test`, `--skip-integration` and `--skip-pdf` give a quicker local loop). The audits of a rendered tree take its paths: `bash .github/scripts/generate-all.sh DIR > trees.txt`, then `bash .github/scripts/shipped-variants.sh $(cat trees.txt)`. No audit sees your own data root: each unsets `SYNTEK_DATA_ROOT` when it starts, and a case that needs a root makes a temporary one. Nor does any audit's git read your global or system git configuration, as in CI, and each sets `UV_PYTHON` to `python3` where you have not set it. CI also runs `python3 migrations/family-update.py --self-test`, `python3 template/.claude/syntek-author-dataroot.py --self-test` and `python3 migrations/agents-outside-link.py --self-test`, which work in temporary folders only, renders four profiles again on the Copier floor `copier.yml` declares and compares them byte for byte with the newest Copier's renders, and runs shellcheck at warning level over every script (the same command locally: `uvx --from shellcheck-py shellcheck -S warning -x migrations/*.sh adopt/*.sh .github/scripts/*.sh template/.claude/hooks/*.sh`).

## Working on the template

Read [`DESIGN.md`](DESIGN.md) first: it is the build contract, and where any other file disagrees with it, `DESIGN.md` wins. [`CONTEXT.md`](CONTEXT.md) maps this repository, and `.claude/CLAUDE.md` is the development manual — token discipline, how to add a skill, a mode file or a gated path, and what to run before committing. Changes are recorded in [`CHANGELOG.md`](CHANGELOG.md).
To propose a change, start with [`CONTRIBUTING.md`](CONTRIBUTING.md); report a vulnerability only as [`SECURITY.md`](SECURITY.md) says.
