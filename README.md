# syntek-author

**A Copier template that generates writing repositories — a theology book, a novel or a business document library — with their own folder system, standards and a Claude Code skill suite.**

![Version](https://img.shields.io/badge/version-0.5.0-blue)
[![Licence: MIT](https://img.shields.io/badge/licence-MIT-green)](LICENSE)
![Template: Copier](https://img.shields.io/badge/template-copier-blue)

```bash
uvx copier copy --trust gh:Syntek-Dev/syntek-author my-book
```

Copier asks its questions, renders the tree for the variant you choose, runs `git init`, and (for a project with references) builds the citation database.
How many questions it asks depends on your answers: the fiction kits only appear for a novel, the business settings only for a library.

## What it generates

One template, three variants. You choose the variant once, with `DOC_TYPE`, and it cannot be changed later.

| Variant    | For                                  | Content layer            | What is particular to it                                                                                                                                                                                                                                          |
| ---------- | ------------------------------------ | ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `theology` | A Christian non-fiction book         | `manuscript/` (chapters) | The six claim categories, argument maps, contested readings, steelmanning; references on by default                                                                                                                                                               |
| `fiction`  | A novel                              | `manuscript/` (chapters) | `world/` (characters, places, the names register), causality, timeline, continuity and character arcs                                                                                                                                                             |
| `business` | Business, legal and client documents | `library/` (documents)   | The document families you choose (`business`, `legal`, `email`, `accounting`, `social-media`, `msp-scp`), each with its folder, standard, skill and create workflow; the document register, review schedule, approvals, brand and disclaimers, LaTeX deliverables |

Every variant shares the same spine:

- **The authoring loop.** The AI drafts one small section (`draft-section`), or you draft and the AI proposes changes as a diff with a reason for each (`improve-section`); your notes drive targeted revisions (`adapt-section`); only your word moves a section into the unit (`promote-section`); and the template learns your voice from what you changed and rejected (`learn-voice`).
- **Provenance.** Every section keeps a ledger entry holding its original (the AI's draft, or yours), every revision with who made it (an AI suggestion you accepted, the AI applying your own note, or your own edit) and your final text. `make provenance` prints a per-unit disclosure table for publishers, and `make compare` prints the three-stage comparison of each section — original, AI edit, final — as a PDF in `build/compare/`: a redline marking every added or removed word by who changed it, in colour-blind-safe colours with a line style of their own, so it reads in greyscale too, and a landscape page with the three stages side by side.
- **Review.** Structure, fact-check, comprehension, flow, grammar and spelling, plus the variant's own checks, run as a workflow against numbered verification gates.
- **Production layers** (`planning/`, `research/`, the content layer, and `proposal/` or `world/` where they apply), each with reference guides, numbered workflows and a place for your own procedures. **Supporting layers** (`standards/`, `tooling/`) and working folders (`handoffs/`, `learning/`, `assets/`).
- **Claude Code configuration.** Skills only, no agents; the rules in `.claude/rules/syntek-author/`; hand off, never compact, with a hook that blocks automatic compaction and one that advises a hand-off as the context window fills. The working-practice skills and both hooks are shared with companion templates (DESIGN.md D51).
- **Other coding agents.** Codex, Gemini CLI, Antigravity and OpenCode read the same rules and skills through a bridge file, with their own settings written once (see [below](#codex-gemini-cli-antigravity-and-opencode)).
- **Binary files outside Git.** A new project files its scans, signed and issued copies, large images and generated audio under a data root you name on each machine, each listed with its checksum, so the repository keeps the text; `DATA_STORE=repo` keeps them in the repository instead (see [below](#binary-files-and-the-data-root)).
- **Two MCP servers**, pinned and keyless: Scrapling for web pages and code-review-graph for a local map of the project's code, with a prompt before each tool that opens a browser or fetches through one (`screenshot`, inside a session already open, apart) and each that writes files (see [below](#mcp-servers-scrapling-and-code-review-graph)).

Options add to a variant:

| Option                      | Offered for                | Default                                                                             | Adds                                                                                                                                                                                                                                                                                 |
| --------------------------- | -------------------------- | ----------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `INCLUDE_PROPOSAL`          | books                      | on                                                                                  | `proposal/`: the book proposal and endorsements (theology), or the query package and submissions tracker (fiction)                                                                                                                                                                   |
| `INCLUDE_REFERENCES`        | all                        | theology only                                                                       | A SQLite references database → CSL-JSON → Pandoc in Harvard style, and the `add-reference` skill                                                                                                                                                                                     |
| `INCLUDE_SENSITIVE_CONTENT` | books                      | off                                                                                 | The sensitive-content standard, the `sensitivity-pass` skill and safe handling for testimony                                                                                                                                                                                         |
| `INCLUDE_WORLDBUILDING`     | fiction                    | on for fantasy and science fiction                                                  | Creatures, cultures and quests                                                                                                                                                                                                                                                       |
| `INCLUDE_CONLANG`           | fiction with worldbuilding | on with worldbuilding                                                               | Constructed languages: phonology, grammar, lexicon, etymology, a writing system and pronunciation                                                                                                                                                                                    |
| `DATA_STORE`                | all                        | `external` on a new project; `repo` on an existing project's first update to v0.5.0 | `external`: three nested `.gitignore` files (`library/src/`, `research/src/`, `proposal/src/`) keep binary files out of Git, and you file them under each machine's data root instead (see [below](#binary-files-and-the-data-root)); `repo` keeps them in the repository, as before |
| `DATA_PROVIDER`             | all                        | `none`                                                                              | Which service keeps a copy of the data root; it only tailors the data-root checks, except in business with `google-drive` and `DATA_STORE` repo: GitHub workflows that push the library to Google Drive and pull it back (see [Providers](#providers))                               |
| `BUSINESS_FAMILIES`         | business                   | every family but `msp-scp`                                                          | One document family per choice: its folder in `library/src/` (with `templates/`, client folders and `drafts/`), its standard in `library/docs/reference/`, its `<family>-documents` skill and its create workflow. `business` is always included                                     |
| `SEED_EXAMPLES`             | all                        | on                                                                                  | One worked example unit (and, with the constructed-language kit, a tiny example language)                                                                                                                                                                                            |

## Generating a project

From the published template:

```bash
uvx copier copy --trust gh:Syntek-Dev/syntek-author my-book
```

From a local clone, rendering the checkout you have rather than the latest release tag:

```bash
uvx copier copy --trust --vcs-ref=HEAD "$(realpath ../syntek-author)" my-book
```

The template path must be absolute, as `"$(realpath ../syntek-author)"` makes it, because Copier records it in the answers file and every later update reads the template from there; a relative path makes every update fail with 'Updating is only supported in git-tracked templates'.
A project rendered from `HEAD` must also be updated with `--vcs-ref=HEAD` (still with `-a .copier-answers.syntek-author.yml`) until a newer release tag exists, because Copier refuses to move it back to the older tag.
That absolute path is then in the answers file you commit, so generate real projects from `gh:Syntek-Dev/syntek-author`, and keep a local clone for trying the template out.

**The `MissingFileWarning` is expected.** On a fresh copy, an adoption and (with Copier 9.18) every update, Copier may warn that `.copier-answers.syntek-author.yml` was not found, and that `.copier-answers.syntek-media.yml` was not found. Both are harmless. The template looks for your previous answers so that an update can refuse a changed `DOC_TYPE`, and for the other syntek template's answers so that both keep one data-root layout; on a first copy, or without that template, there are none.

**Why `--trust`.** After rendering, the template runs four small tasks: `git init` (only where no repository exists), `chmod +x` on the session hooks, `make init` to build the references database, and a record of the rendered template inside `.git` that the first update's report compares against (see [Updating a project](#updating-a-project)). Copier treats any task as an unsafe feature and refuses to run one without `--trust`. Every task is non-fatal: if `sqlite3` or `make` is missing, the project is still complete and you run `make init` later.

Without prompts, for scripts and CI, pass every answer that has no default and accept the rest:

```bash
uvx copier copy --trust --defaults \
  --data DOC_TYPE=fiction \
  --data "PROJECT_NAME=The Salt Ferry" \
  --data "PROJECT_DESCRIPTION=A ferry pilot on a drowned coast must carry a stranger across the salt marsh before the spring tide." \
  --data "AUTHOR_NAME=Robin Example" \
  --data DATE=03/10/2026 \
  gh:Syntek-Dev/syntek-author the-salt-ferry
```

`DOC_TYPE` has no default on purpose: without it, `--defaults` stops with an error rather than quietly generating a theology book.

When generation finishes, open the project in Claude Code. The generated `README.md` and `CONTEXT.md` describe that project; `.claude/CLAUDE.md` holds its brief and points at the rules. A project that answered `DATA_STORE` external (the default) also prints the three steps that set up a machine's data root ([Binary files and the data root](#binary-files-and-the-data-root)); text work needs none of them.

**Your own defaults.** Copier reads a `defaults:` map from your user settings file, `~/.config/copier/settings.yml` (or the file `COPIER_SETTINGS_PATH` names), so a machine's own choices, such as `OPENCODE_PROVIDER: llama-cpp` and its model, live there and no template hard-codes them. One file serves every template that asks a question of the same name. `--data` and recorded answers beat it (on a copy, only when it is given `-a .copier-answers.syntek-author.yml`), and on an update it fills only the questions new to the project. `defaults: {}` is the minimum content: an empty file crashes Copier 9.17.1. A value outside a question's choices fails every copy, even one in which that question is never asked. Never put `AGENT_CLIENTS` there: it replaces the default of none on the update that first asks it, and the recorded clients on a copy over a generated project, so it records clients whose files the project never received. Re-running `copier copy` over a generated project keeps the clients its answers file records; only a record from before the question existed defaults to none, so pass `--data 'AGENT_CLIENTS=[…]'` there. The data-root questions carry the same trap: never set `DATA_STORE` or `DATA_SLUG` there, set `DATA_AREA` or a kind folder only where it equals every other syntek template's recorded answer, and leave `DATA_PROVIDER` out, which there replaces the mapping from `INCLUDE_DRIVE_SYNC` ([Binary files and the data root](#binary-files-and-the-data-root)).

## The project's settings: `00-project.md` and `project.mk`

Every project gets two settings files, written once from your answers and never overwritten by `copier update`. They are where the project tells the template how it works.

**`.claude/rules/syntek-author/00-project.md`** sits with the template's rules, so Claude Code loads it at the start of every session, and it outranks every other file in that folder. The template's rules and skills read project-specific values from it, by heading, and from nowhere else:

| Heading               | What it holds                                                                                                                                                                                                                                                                                                                                                                                                   |
| --------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `## Brief`            | The audience, the reader test and the variant's answers: the Bible translation, the genre, or the trading name, voice, jurisdiction and currency.                                                                                                                                                                                                                                                               |
| `## Paths`            | Where the project keeps each thing the template names by role: the project brief and rules, handoffs and their filename form, decision maps, research notes, the ledger, and for business the approval records, the brand folder, disclaimers, client facts and the LaTeX skeleton. Change the path, never the role.                                                                                            |
| `## Memory headings`  | The six headings the template's files use in `.claude/MEMORY.md`, mapped to the headings this project uses.                                                                                                                                                                                                                                                                                                     |
| `## Workflow aliases` | A template workflow, by its full folder name, and the project's own procedure to run instead. Empty until you add one.                                                                                                                                                                                                                                                                                          |
| `## Overrides`        | A template rule this project does differently, such as how questions are asked; and **redirects**, one bullet each, `` `<template path>` → `<project path>` ``, for a template path with no role in `## Paths` (a family standard, a guide, a drafts folder): every template file then reads and writes the project's path instead. A redirect never points into a folder git ignores. Empty until you add one. |

When an answer changes later, change it here by hand: Copier never rewrites the file.

**`tooling/project.mk`** holds the build settings the `Makefile` reads before anything else: `LOGO_DIRS` (where TeX looks for a logo first), `FLAG_EXTRA_RE` (the project's own open-item marks, which `make flags` counts beside `AUTHOR TO CONFIRM` and `VERIFY`; business starts with `[AWAITING USER INPUT]` and `\fillme`), `MAINFONT`, `SANSFONT` and `MONOFONT` (the typefaces of a Markdown PDF), and for business `BRAND_DIRS` (where `make flags` looks for the brand files; `standards/brand` by default: point it at your own brand folder, or the template's brand seeds, which an update restores if deleted, keep their open slots counted for ever), `DOCX_CONVERTER` and `ISSUE_STATUSES` (the statuses at which `make pdf FILE=… ISSUE=1` may issue a document; `final` by default). A setting that differs from one project to the next belongs here, never in the `Makefile`. It never sets `SYNTEK_DATA_ROOT`: the data root is each machine's, never the project's.

**The context window.** The hand-off hook (`.claude/hooks/context-threshold-handoff.sh`) advises a hand-off once at 50% of the context window and insists at 75%, assuming a window of 200,000 tokens. If your sessions run with a larger window, set its size for this project in `.claude/settings.local.json`, as `"env": {"CLAUDE_CONTEXT_WINDOW": "1000000"}`, or export `CLAUDE_CONTEXT_WINDOW` in the shell that starts Claude Code. `CLAUDE_CONTEXT_ADVISE_PCT` and `CLAUDE_CONTEXT_INSIST_PCT` move the two thresholds.

Two build rules come with them. `make pdf FILE=… ISSUE=1` refuses to overwrite a PDF already issued unless you add `FORCE=1`, and refuses a document that still has an open flag whatever `FORCE` says; `ISSUE` and `FORCE` take only `1`, `yes` or `true`. Under `DATA_STORE` repo the issued copy sits beside its source and `FORCE=1` replaces it; under `external` it is filed under the data root, and `FORCE=1` files the new copy and keeps the old one, marked superseded. And no `make` target reads a file git ignores: `make flags`, `make lint` and every other scan skip ignored folders, because they hold credentials and local-only material and the targets print what they find. The one exception is the data-root tool behind `make files-*`, which copies or hashes only a file you name or a manifest lists.

## Binary files and the data root

Git keeps text well and large binary files badly: each one stays in every clone for ever. So a new project keeps its binary records and issued copies (scans, signed and received documents, issued PDF and Word copies, archived email, large images, generated audio) outside the repository, under a **data root**: one folder on each machine, which you name, set up and back up yourself (DESIGN.md D50). The repository keeps the text, and a manifest in each filing folder, `external.toml`, lists every filed file with its checksum, so a copy that goes missing or changes is found. `DATA_STORE` decides it: `external`, a new project's default, or `repo`, which keeps the files in the repository as before; an existing project records `repo` on its first update to this release, and so does an adoption.

**On each machine you work on, once:**

1. Choose the data root: a folder outside every repository, on a local disk or a mounted share. Set the environment variable `SYNTEK_DATA_ROOT` to its absolute path in your shell profile (`export SYNTEK_DATA_ROOT="$HOME/syntek-data"`), or in the system's environment settings on Windows, so that Claude Code, `make` and your terminal all see it. No file in a project names it, and `tooling/project.mk` must never set it: an empty `SYNTEK_DATA_ROOT =` there hides the variable.
2. Create the empty marker file at its top: `touch "$SYNTEK_DATA_ROOT/.syntek-data-root"`. Nothing is filed under a folder without it, which also catches a network disk that is not mounted (its mount point is an empty folder). The tool never creates it.
3. Run `make root` in a project: it checks the root, prints where each kind of file goes, and prints the checklist for the provider you answered ([Providers](#providers)).

A copy that answers `external` prints these steps when it finishes. Text work never needs a root: drafting, proofs, `make flags`, `make lint` and `make compare` run without one. Issuing and filing stop with exit `2` and the reason, and never fall back to writing into the repository.

**The layout.** Every file goes to `<root>/<DATA_AREA>/<kind folder>/<DATA_SLUG>/<its path in the repository>`, so it keeps its frozen name and every reference to it keeps its path. A signed NDA in a business project answered with the defaults, in a folder named `client-documents`, goes to `$SYNTEK_DATA_ROOT/business/docs/client-documents/library/src/legal/client-docs/example-client/nda-example-v1-0-02-03-2026-signed.pdf`. The kind folder (`DATA_KIND_DOCS`, `DATA_KIND_PHOTOS`, `DATA_KIND_AUDIO` or `DATA_KIND_VIDEOS`) follows the file's extension, except that everything under `library/src/` is a document. The filing folders are this template's map, `.claude/syntek-author-dataroot.json`: `library/src/`, `research/src/`, `proposal/src/`, `assets/` (where `make files-status` warns about a file over 1 MiB) and `world/src/` (generated audio). Another syntek template's map names its own folders, and may mark one as working output (`"rows": "none"`), which never takes a row and which `make files-status` and `make files-verify` never list; a folder two maps claim is refused. Prose names a filed file `` `ext:<its path in the repository>` ``. The tool's `path`, and a business build under `external`, look in the work tree first and then under the root.

**The commands.** The `Makefile` runs the data-root tool, `.claude/syntek-author-dataroot.py` (`python3 .claude/syntek-author-dataroot.py --help` lists every subcommand):

| Command                        | What it does                                                                                                                                                                                                                                                                                                                                                                                                         |
| ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `make root`                    | The root, its marker, this project's layout under it, and your provider's checklist                                                                                                                                                                                                                                                                                                                                  |
| `make files-add FILE=… ROLE=…` | Files a copy of `FILE` under the root and lists it, after the Windows-safe name and case checks. `AS=` files it at another path in the repository (by default `FILE`'s own), `SOURCE=` names the file it came from, `LABEL=` says where else a copy is kept (a label, never a URL), and `FORCE=1` files a new copy over a listed one, keeping the old one marked superseded (never over an evidence copy: see below) |
| `make files-status`            | The loss check: binaries Git ignores in a filing folder that no manifest lists, large files in `assets/`, filed folders that no longer match the answers, files under this project's folders of the root that no manifest lists (those outside every template's filing folders included, never those in a working-output folder), and a role two templates' maps define differently                                  |
| `make files-verify`            | Checks every listed copy against its checksum, and fails where a row committed at `HEAD` has been removed or changed (other than its `state`), or a committed `external.toml` lies in no template's filing folder; `GLOB=` narrows it, and a file the system keeps online-only is skipped unless `HYDRATE=1`                                                                                                         |
| `make files-pull`              | Copies listed files into the work tree, where Git ignores them, checking each checksum; `GLOB=` narrows it                                                                                                                                                                                                                                                                                                           |
| `make files-plan`              | Lists the binaries Git still tracks in the filing folders, where each would go and every conflict; `COPY=1` copies them there                                                                                                                                                                                                                                                                                        |
| `make pdf FILE=… ISSUE=1`      | Business: files the issued copy under the root, with its manifest row, instead of beside its source                                                                                                                                                                                                                                                                                                                  |

**Roles and rows.** `ROLE` is one of the shared roles, `issued`, `signed`, `ingested`, `received`, `archive`, `evidence`, `asset` and `generated`, or a role another syntek template's map adds: lower-case words joined by hyphens, such as `brand-export`, never a shared role's name or a kind's. A `signed`, `evidence`, `ingested` or `received` copy is evidence, and so is one whose map role says `"evidence": true`. Each row records its `evidence` flag when it is filed and keeps it; a row is protected where its flag or any map present says so (where two maps define a role differently, evidence wins), and a row whose role no map present defines is reported and treated as evidence. An evidence copy's file and checksum are never replaced: `FORCE=1` refuses it, so file a new version under its own name, and a changed file is a failure, never an update. Nothing filed is overwritten or deleted, and a manifest's rows are never removed or rewritten: a file is copied to a temporary name, checked against its checksum, and only then listed, and the one change to a row is its `state`, from `current` to `superseded` or `withdrawn`; a superseding copy is a new row whose `replaces` names the copy kept. A key the tool does not know, written by a newer template, is kept and ignored, and a map or manifest newer than the tool, or one that does not parse or is invalid, is reported and stops only the commands that touch that map's folders, so another template's newer map never stops this one's issuing. The tool exits `0` when it is done, `1` when a check fails and `2` when it cannot act. It is the one exception to 'no target reads a file Git ignores': it copies or hashes only a file you name or a manifest lists, and lists any other by name and size only.

**What stays in Git.** Under `external`, three nested `.gitignore` files (`library/src/`, `research/src/`, `proposal/src/`) keep new binaries out of Git; they never ignore `external.toml` or a `README.md`, and you commit each manifest with the work it lists. An ignore rule never untracks a file, so binaries Git already tracks stay tracked until you move them: `make files-plan` lists them, `make files-plan COPY=1` copies them under the root, and untracking the originals is yours, after `make files-verify`. Untracking deletes them from every other clone's work tree when it pulls that commit, so set up and verify the root on every machine first. `build/`, `assets/` (which has no ignore file), the ignored language audio in `world/src/` and `tooling/references.db` are unchanged. Under `repo` nothing changes: `make root` says the root is not used, issuing writes beside the source, `make files-add … ROLE=generated` writes nothing and exits `0` (generated files stay git-ignored in the work tree), as does a role whose map entry says `"repo": "skip"`, unless the root and the repository contain one another or a marker sits above the repository, where both refuse first ('Disks and names' below); any other role says to commit the file instead.

**Keep the layout answers.** `DATA_AREA`, `DATA_SLUG` and the four kind folders decide where files go, and every syntek template in a project uses the same ones: a template's first answers default to the other's recorded ones and must equal them, case included. A later difference is allowed and reported after the update, and both templates' data commands then refuse until the answers agree again; a template not yet updated to this release, which records no store, only gives a warning. A change of case alone is refused, because one disk treats `Business/` and `business/` as one folder and another as two. Any other change leaves the files already filed under the old folder, where the manifest still finds them (each row records the folder it was filed under), and `make root` names that folder with the `--data` answers that restore it. Answering `DATA_STORE` repo forgets these answers, because Copier drops an answer it no longer asks: note them first, and pass them again with `--data` if you return to `external`. Two projects with the same `DATA_SLUG` in one area share a folder, and each then sees the other's files as unlisted: give every project its own.

**Copier settings files.** A `defaults:` value for a data-root question replaces its whole default, the other template's recorded answer and `repo` on the first update included, and Copier cannot tell it from `--data`. Never set `DATA_STORE` or `DATA_SLUG` there, and set `DATA_AREA` or a kind folder there only where it equals every other syntek template's recorded answer.

**Disks and names.** Windows, NTFS and SMB refuse `:` and the other reserved characters, device names such as `CON` and a trailing dot or space, and limit the length of a path. Every `add` checks the names, and `python3 .claude/syntek-author-dataroot.py check-names` checks a path, or the whole layout, and warns beyond 260 characters. On Linux, mount an NTFS disk with `windows_names`. Copies are verified by checksum only, never by size or date, which network disks report differently. Never put a repository inside the data root or inside a synced folder, nor the data root inside a repository: a sync service copies file by file and corrupts Git, so, under either store, every data command refuses a root and a repository that contain one another, or a marker above the repository, except `make files-status`, which warns that it did not check the copies.

**The guard.** A new project's `.claude/settings.json` wires a `PreToolUse` hook that runs the tool's `guard`: Claude Code cannot edit or write a file under a data root, found from `SYNTEK_DATA_ROOT` or by its marker, nor search there with its own `Grep` and `Glob` tools. On macOS, Linux and WSL, Claude Code searches through the shell, which the guard does not read, so there it stops edits and writes, not searches, and the rules alone keep a session from listing the root; other clients have no guard and follow the rules. The guard never blocks work outside a data root, and exits `0` on any error of its own. An update never wires it into an existing `settings.json`; to wire it, add this entry under `"hooks"` in `.claude/settings.json` (the v0.5.0 update prints the same):

```json
"PreToolUse": [
  {
    "matcher": "Edit|Write|MultiEdit|NotebookEdit|Grep|Glob",
    "hooks": [
      {
        "type": "command",
        "command": "bash -c 'ROOT=$(git rev-parse --show-toplevel 2>/dev/null) || exit 0; for f in \"$ROOT\"/.claude/syntek-*-dataroot.py; do [ -f \"$f\" ] && exec python3 \"$f\" guard; done; exit 0'",
        "timeout": 10
      }
    ]
  }
]
```

**Removing a template.** Remove its answers file with it: another template's answers file left in the project still binds this template's first data-root answers.

### Providers

`DATA_PROVIDER` records which service keeps a copy of the data root (DESIGN.md D53). **You set it up and run it.** The template never installs, configures, schedules or runs a sync client, mount or job, never writes a provider's configuration and never calls its service; the answer only tailors `make root`'s checklist and the data-root checks. Point the service at the data root, never at a repository: Git's own advice is never to sync a repository with a cloud service, and the tool warns where a repository sits under a known sync folder.

| Value                | Ships                                                                                                | What the data-root tool adds                                                                                                                                                                                                                                                               |
| -------------------- | ---------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `none` (the default) | nothing                                                                                              | 'Back it up yourself'; a warning if the root sits under a sync folder anyway                                                                                                                                                                                                               |
| `google-drive`       | in business with `DATA_STORE` repo, `.github/`: the Drive push and pull workflows; otherwise nothing | Drive for desktop in mirror mode, or the data root under 'Folders from your computer'; on macOS the fixed place under `$HOME/Library/CloudStorage`; on Linux, which has no Drive client, rclone; Drive's `lost_and_found` folder, and names that a Windows or macOS disk cannot hold twice |
| `onedrive`           | nothing                                                                                              | The root inside the OneDrive or SharePoint library folder, kept on this device; OneDrive's reserved names refused and paths over 400 characters warned                                                                                                                                     |
| `dropbox`            | nothing                                                                                              | The root inside the Dropbox folder on a local disk, never on a NAS, available offline; never mark it 'ignored', which deletes the cloud copy                                                                                                                                               |
| `other-cloud`        | nothing                                                                                              | A tool you run, such as rclone: `sync` deletes what the source lacks, so try `--dry-run` first; `bisync` with the marker as its check file                                                                                                                                                 |
| `nas`                | nothing                                                                                              | An SMB or NFS share, on the LAN or over WireGuard: the marker shows an unmounted share; hard NFS mounts; names kept Windows-safe                                                                                                                                                           |

For every value, `make files-status` adds a hint where an unlisted file's name looks like a provider's conflict copy (never rename or delete one: compare it first), and `make files-verify` never opens a file the system keeps online-only, which a read would download, unless `HYDRATE=1` asks for it. Every syntek template in a project defaults to the same answer, and a difference is reported, never refused, because it moves no file.

**The Google Drive workflows** ship only in business with `google-drive` and `DATA_STORE` repo. They run on GitHub's servers with your own secrets (Workload Identity Federation, no stored key) and never touch the data root, which a GitHub runner does not have. Any other answer, or the `external` store, deletes `.github/`, your edits included, on the next update. Each v0.5.0 workflow also stops itself before it authenticates when the answers file records any store but `repo`, so a v0.5.0 copy you keep or restore cannot bin the Drive copies of files you move out of Git. A copy from before v0.5.0 has no such step: the update that crosses v0.5.0 lists the ones it deleted, and restoring one from its report brings back a workflow that would. Three cautions:

- **A Copier settings default for `DATA_PROVIDER`** replaces the mapping from the old `INCLUDE_DRIVE_SYNC`: with `--defaults`, the update that first asks it can delete a business project's live Drive workflows. Do not set it there.
- **A fresh business copy beside another syntek template that records `repo` and `google-drive`** takes both, so under `--defaults` it ships the Drive workflows unasked, and they fail until their secrets exist.
- **Drive workflows the template does not manage** (your own, or ones restored after an answer deleted them) still run, and under the `external` store the commit that untracks binaries makes their push bin every Drive copy. The v0.5.0 update lists them, and the pre-v0.5.0 ones it deleted (its report offers to restore any you had edited): disable or delete them first, and restore one only to disable it or to add the store guard step. One restored after that update is listed only when you run its migration again (the command ends its report).

## What `copier update` will and will not touch

Every file in a generated project belongs to one of five classes. Knowing which is which is the whole of updating safely.

**1. Template files — updated, and merged with your edits.**
The rules in `.claude/rules/syntek-author/`, the skills (apart from the shared ones in class 5) and their mode files, every folder's `CONTEXT.md` and `CLAUDE.md` (apart from the seeded ones below), the reference guides in `docs/reference/`, the numbered workflows, the standards (apart from the seeds below), `tooling/`, the `Makefile`, and the data-root tool `.claude/syntek-author-dataroot.py` with its map (and, under `DATA_STORE` external, the three nested `.gitignore` files of `library/src/`, `research/src/` and `proposal/src/`).
An update brings the template's improvements and keeps your local edits through a three-way merge; where both changed the same lines you get a conflict to resolve.
Better than editing them: put your own guide in `docs/project/` (a guide there with the same name overrides the reference guide), your own procedure in `workflows/local/` (a local workflow with the same name overrides the template's), and your own rules in `.claude/CLAUDE.md`.

**2. Seeds — written once if missing, then yours.**
The project's settings, `.claude/rules/syntek-author/00-project.md` and `tooling/project.mk` (see above), `README.md`, `CONTEXT.md`, `.gitignore`, `.mcp.json`, `.claude/CLAUDE.md`, `.claude/CONTEXT.md`, `.claude/MEMORY.md`, `.claude/settings.json`, the `CONTEXT.md` and `CLAUDE.md` of `.claude/skills/`, the style sheet, voice notes, terminology and provenance table in `standards/style/`, the outline and the variant registers in `planning/src/`, the map index `planning/src/maps/CONTEXT.md`, the `CONTEXT.md` and `CLAUDE.md` of every `docs/project/` and `workflows/local/` (you add a row to them), the names register and the history's `eras.md`, the brand voice, brand guide and disclaimers, the permissions register, the page design and `book.tex` in `typeset/src/`, the proposal stubs and trackers, and `tooling/seed-refs.sql`.
An update never overwrites one that exists. If you delete one, the next update puts a fresh, empty copy back, because skills and rules read it by path. Two seeds gain entries: on a copy over a `.claude/settings.json` you already have, and on every update, the template adds the hook entries and permission rules it lists, and `"autoCompactEnabled": false` where the file has no such key, only adding, never removing, reordering, weakening or changing a value you set; and `.mcp.json` gains the template's two MCP servers, once each, the same way (see [Shared files and settings on update](#updating-a-project)).
The cost: once a seed exists it never receives the template's improvements. A release that must change a seed ships a migration that edits your copy only where exactly one change is correct, and lists the rest.
**The one exception: turning an option off deletes every file it generated, seeds included**, even ones you have filled in; dropping a document family deletes its template files (no family folder ships a seed) and, in an additively adopted repository, your own files at those template paths (see [Updating a project](#updating-a-project)).

**3. Examples — copied once, and they stay deleted.**
The example chapter or proposal, its brief, and the example language. They arrive on the first `copier copy` (unless `SEED_EXAMPLES` is false) and an update never renders them again: delete them when you are done and they never come back; keep and edit them and an update leaves them alone.

**4. Your folders — the template ships only the signposts.**
`docs/project/`, `workflows/local/`, the unit briefs in `planning/src/units/`, maps and reviews, every folder of sources, evidence and notes in `research/src/`, every folder in `world/src/`, the voice samples and ledger in `standards/style/`, `handoffs/` (whose signposts are class 5), `learning/` and `assets/`.
The template ships each folder's `CONTEXT.md` and `CLAUDE.md` and nothing else, so nothing you put there is ever touched. The data-root manifests, `external.toml` in each filing folder, are yours too: the data-root tool writes them, and Copier never renders them. Where you add rows to the pair itself (`docs/project/`, `workflows/local/` and the map index), the pair is a seed (class 2), so an update never merges into your rows.

**5. Copy-only agent files — written once, and never again.**
`AGENTS.md`, `GEMINI.md`, the `skills` link and `mcp_config.json` in `.agents/`, `.codex/`, `.gemini/` and `opencode.json`, for the clients `AGENT_CLIENTS` chose. A copy writes them where they are missing; an update never renders them, so your edits stand (apart from the template's two MCP servers, which the update adds once to a file that lacks them), a file you delete stays deleted, a client you add later is set up by hand (below), and a client you remove keeps its files until you delete them. The bridge they point to, `.claude/syntek-author-agents.md`, and the permissions script, `.claude/syntek-author-permissions.py`, are template files (class 1) and ship in every project, whichever clients it has.

**Shared working-practice files — written once, refreshed only where you have not changed them.**
The `SKILL.md` of `grill-me`, `grill-with-docs`, `grilling`, `handoff`, `wait-what`, `wayfinder` and `to-questionnaire`, the two hooks in `.claude/hooks/` with that folder's `CONTEXT.md` and `CLAUDE.md`, and the `CONTEXT.md` and `CLAUDE.md` of `handoffs/` are shared byte for byte with companion templates such as syntek-media, so either template can write them and neither owns them (DESIGN.md D51). They are copy-only like the agent files, with one difference: after each update, a file whose bytes still equal a version this template recorded here is replaced by the new one, one new in that release that the project never had is written, and a file you have edited, or one holding a companion template's version, is kept and listed in the update report (that template's own update refreshes it). Put project tailoring in `.claude/CLAUDE.md` or the rules, not in a shared `SKILL.md`. The theology, fiction or business mode file beside each skill is a template file (class 1); a companion template's own mode files beside it (syntek-media's `MEDIA-*.md`) apply only to that template's work. A skill of the same name in your own `~/.claude/skills/` replaces the project's in Claude Code, because personal skills take precedence over project skills: `/handoff`, and the hooks that ask for the handoff skill, then run yours, which no update refreshes. Rename or remove the personal one to use the project's.

Your prose is never a template file: drafts, promoted sections and ledger entries are yours in every class above.

## Updating a project

Always on a branch, always with the answers file named, and with Git's automatic housekeeping off for the run:

```bash
git switch -c update-syntek-author
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx copier update --trust -a .copier-answers.syntek-author.yml
git status && git diff     # review; resolve any conflict markers
git add -A && git commit -m 'Update from syntek-author'
```

**Why housekeeping off.** Copier renders the template into temporary Git repositories and commits in them, and after a commit Git may start its automatic maintenance in the background. If that is still writing when Copier deletes the temporary folder, the update stops with `OSError: [Errno 39] Directory not empty` on a `.git/objects` path under a `copier._main.old_copy.…` or `copier._main.new_copy.…` folder. It is intermittent, most likely with Git 2.54 or 2.55 (Git 2.56 starts the background repack only above about 7,000 loose objects) and with several updates running at once. The five variables in front of the command turn `gc.auto` and `maintenance.auto` off for that one command, in every Git it starts, and change none of your Git settings. The form is for POSIX shells such as bash and zsh, and needs Git 2.31 or later. Give every other update command in this README the same five variables in front.

**If an update stopped with that error,** Copier had already written the new version's files and recorded the new version in `.copier-answers.syntek-author.yml`, but nothing that runs after the render had run: no after-stage migration (the release's own report, such as v0.5.0's, included), no update report, no refresh of the shared files, no settings entry or MCP server added, no message after the update, and an `.agents` link outside the project is still held aside. Never commit that state: an update run over it takes the new version as already reached, so it reports '0.5.0 → 0.5.0' and skips that release's migrations. Discard it and run the update again, from the project root, in this order. First, if `.agents.syntek-held` exists, put the link back as 'An `.agents` link outside the project' below says: `git clean -fd` would delete it. Next run `git clean -n -d`, a dry run that deletes nothing: it lists every untracked file and folder the discard would delete, not only the update's (Copier refuses to start over untracked files only where Git shows them: with `status.showUntrackedFiles` set to `no`, it runs over yours), so commit or move out of the project anything of yours it lists; files Git ignores are left alone. `git reset --hard` discards every uncommitted change in the repository, so the project must be its own repository. Then:

```bash
git reset --hard && git clean -fd
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx copier update --trust -a .copier-answers.syntek-author.yml
```

The second run reports from the version you had ('0.4.0 → 0.5.0', say), runs every migration the crossing calls for, and delivers what an update that never stopped delivers.

Discarding an update (`git reset --hard` with `git clean -fd`, after the `git clean -n -d` dry run above, or `git stash -u`) and running it again is safe: the second run delivers what the first did. Until you commit it, an update counts as not made, so a rerun offers again everything the first run offered, and a settings entry or MCP server you removed from its uncommitted result comes back: remove it again once the update is committed.

Run template updates on one line of history: the update's record is kept per clone, not per branch, so update on a branch cut from your main line and merge it, and bring other long-lived branches up to date by merging rather than by running `copier update` on each.

A formatter or a pre-commit hook may rewrite `.copier-answers.syntek-author.yml` before you commit it: the update matches its record to the answers the file holds, not to its bytes, so re-indented lists, another kind of quotes, comments, a leading `---` and another key order change nothing. Keep away from it anything that changes the answers themselves (a formatter that unquotes `'yes'` or `'007'` changes what Copier reads) or writes YAML the update cannot read for certain (anchors, tags, block scalars, a list in brackets over several lines): the update then compares the file byte for byte, finds no record of what earlier updates offered and runs as for a project with no record, so a settings entry you removed before committing can come back. A project whose answers file a formatter rewrote before v0.5.0 runs its first update to v0.5.0 that way once; from the next update on, the record is found.

**The update report.** Every update ends with a report of each file the new version changed that the update did not deliver to you, and why, with a command to compare and a command to take the template's version. It changes none of your files apart from the shared files it refreshes (class 5), never commits, needs no network, and never stops the update. An example, from an update with a conflict and some files kept back:

```text
▸ syntek-author: refreshed 2 shared files you had not changed: .claude/skills/handoff/SKILL.md, .claude/skills/grill-me/SKILL.md
▸ syntek-author update report, 0.3.0 → 0.4.0
  The template changed 38 files here: 30 delivered, 2 merged with your edits, 2 refreshed, 3 kept back, 1 conflict.
  Apart from the refresh above, this report changed none of your files. In every compare, '-' lines are the template's and '+' lines are yours.

  CONFLICT: both versions are in the file between <<<<<<< and >>>>>>>; resolve it, then git add (1):
    planning/CONTEXT.md
        compare: git diff syntek-author/template syntek-author/yours -- planning/CONTEXT.md
        take:    git checkout syntek-author/template -- planning/CONTEXT.md

  NOT UPDATED because you had changed them (2):
    .claude/skills/wayfinder/SKILL.md
        compare: git diff syntek-author/template -- .claude/skills/wayfinder/SKILL.md
        take:    git restore --source=syntek-author/template -- .claude/skills/wayfinder/SKILL.md
    standards/style/style-sheet.md
        compare: git diff syntek-author/template -- standards/style/style-sheet.md
        take:    git restore --source=syntek-author/template -- standards/style/style-sheet.md

  NOT UPDATED because files of this kind are written once: seeds, examples, copy-only (1):
    .gitignore
        compare: git diff syntek-author/template -- .gitignore
        take:    git restore --source=syntek-author/template -- .gitignore

  These commands work offline until the next update. To see the template's whole change to a file:
  git diff syntek-author/template^ syntek-author/template -- <path>
  This report again, with every entry: git log -1 --format=%B syntek-author/template
```

The sections, each printed only when it has an entry:

| Section                                                                            | What it means                                                                                                                                                                                                      | Commands                                               |
| ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------ |
| `CONFLICT`                                                                         | Copier left both versions in the file.                                                                                                                                                                             | `compare`, and `take` (which also clears the conflict) |
| `REJECTED HUNKS`                                                                   | In rej mode: the file holds the template's version, and your lines are in a `.rej` file beside it that this update left (a `.rej` committed earlier, or beside a path the template does not ship, is not counted). | `compare`, `yours`                                     |
| `DELETED by this update although you had changed them`                             | The template retired the file, or an answer (an option turned off, another provider or store) no longer ships it; your version is still in the record.                                                             | `see`, `restore`                                       |
| `DELETED by this update (retired by the template, or by an option you turned off)` | Printed when the old version could not be rendered, so the report cannot tell your edits apart.                                                                                                                    | `see`, `restore`                                       |
| `NOT UPDATED because you had changed them`                                         | A file the template changed that you had edited and the update left as you had it: a seed, an example, a shared file, or a template file Copier did not merge.                                                     | `compare`, `take`                                      |
| `NOT UPDATED because the file holds syntek-media's version`                        | A shared file a companion template wrote.                                                                                                                                                                          | `compare`, `take`                                      |
| `NOT UPDATED because files of this kind are written once`                          | A seed, example or copy-only file you had not changed: an update never rewrites them.                                                                                                                              | `compare`, `take`                                      |
| `NOT UPDATED because it is new in this version and you already had a file there`   | A template file new in this version, at a path where you already had one of your own.                                                                                                                              | `compare`, `take`                                      |
| `NOT ADDED: new in this version, and an update never adds files of this kind`      | A new copy-only file (an agent client's file, say) that only a copy writes.                                                                                                                                        | `see`, `take`                                          |
| `NOT RESTORED because you had deleted them`                                        | A template file you deleted, which the template has since changed.                                                                                                                                                 | `see`, `take`                                          |

Files Copier merged with your edits are counted, not listed: they were delivered. Each section lists up to 25 files, and the last line prints the whole report again.

The commands are plain `git` and need no network. `syntek-author/template` is a ref inside `.git`, `refs/syntek-author/template`: this project's own render of the template version it now records, made with your answers; each update adds a render whose parent is the previous one, so `syntek-author/template^` is the version before. `syntek-author/yours` points at your `HEAD` when the update ran, before any of its changes, so the commands stay right after you commit. `git restore --source=…` changes the file in your working tree only, never the index, and `git diff`, `git restore --staged` or a checkout undoes it before you commit. The refs are local to your clone: `git push`, `git push --all` or `--tags` and an ordinary clone leave them behind, but `git push --mirror`, `git clone --mirror` and `git bundle create --all` carry them (no namespace under `refs/` escapes a mirror). `syntek-author/template` holds the template rendered with your answers, the report, the list of settings entries and MCP servers offered and of the files the report's script wrote, a fingerprint of your answers, and no path of your machine. `syntek-author/yours` holds your `HEAD` at the last update, so it keeps that commit alive after an amend or rebase: if you rewrite history to remove a secret, delete both refs first (`git update-ref -d refs/syntek-author/template` and `git update-ref -d refs/syntek-author/yours`; the next update records them again, rendering the old version once). To mirror a repository without them, configure the remote instead of using `--mirror`: `git config remote.<name>.push '+refs/*:refs/*'`, `git config --add remote.<name>.push '^refs/syntek-author/*'`, then `git push --prune <name>`.

**When the report is slower, or absent.** A project copied with v0.4.0 or later records its render at the copy, so later reports render only the new version: a few seconds. The first update of a project made before v0.4.0, of an additive adoption (`--skip-tasks`) or in a fresh clone (an ordinary push or clone does not carry the refs) renders the old version as well, once (up to about 20 seconds). If no `▸ … update report` line appears at all, Copier skipped its migrations, as it does when it cannot read a template version on either side (a template source that is not a git repository, or an answers file with no `_commit`; an untagged template still gets a version such as `0.0.0.post1.dev0+<hash>`, so its update still reports): run `git status` and look for `.rej` files and conflict markers yourself. The project must be its own git repository: in a folder inside another repository, the update prints one line saying that nothing was recorded, refreshed or added, and names the shared files that are missing. To keep the output short, set `SYNTEK_UPDATE_REPORT=off`: the report then lists only conflicts and deletions, without rendering anything, and that update neither refreshes nor adds a shared file nor offers a settings entry or an MCP server; the next update without it does all of these (as it does after an update whose render failed), except where the update with the report off followed one you discarded and every file the discarded update wrote has been changed since: then add what the discarded update offered by hand.

**Shared files and settings on update.** The update refreshes each shared working-practice file (class 5) whose bytes equal a version this template recorded here, writes one this project never had where it is missing (one you deleted stays deleted, and one an earlier update skipped arrives now), and lists the rest under 'NOT UPDATED because you had changed them', or under the companion template's name where the file holds its version. It then offers `.claude/settings.json` each hook entry, permission rule and top-level value the release lists, once: one already there is left; one missing is added into your file's own text, in its indentation and line endings; one you removed after it was offered is not added again (the record lists every entry offered; without a record, an entry any committed version of the file held counts as offered); a rule you allow yourself is reported, never added; a top-level value is added only where your file has no such key, so an `autoCompactEnabled` you set to `true` is kept, and the copy or update prints one line saying the handoff hooks assume false (set it to false in `.claude/settings.json` to use them); a file that is not plain JSON (comments, say), or that is a link, is reported and never written, and where it can be read (a link to a file inside the project, or a key its text plainly holds) only the entries it lacks are named for adding by hand; a `settings.json` Git ignores is never read: one line names the entries to add by hand, and they are offered again; a hook entry whose script is not in `.claude/hooks/` is reported and offered again by the next update. The file is written only when an entry is added, and if the insertion would not parse back to exactly the planned settings, it is rewritten as JSON in its own key order and indentation and the report says so. A `settings.json` changed only by these additions is counted as the template's, never as your edit, in this and later reports. A copy over a `.claude/settings.json` you already have (a moving adoption, say) does the same. From v0.4.0, that is the `UserPromptSubmit` entry for `.claude/hooks/context-threshold-handoff.sh`, which advises a hand-off once the session has used half its context window and insists at three-quarters (200000 tokens unless you set `CLAUDE_CONTEXT_WINDOW`), and `"autoCompactEnabled": false`, which the handoff hooks assume: a project adopted over a `settings.json` of its own without that key gains it; from v0.5.0, also the eight asks and the deny of the two MCP servers. It then offers `.mcp.json` and each client file you have the template's MCP servers, once each, in the same way.

**Why `-a`.** The answers file is called `.copier-answers.syntek-author.yml`, not Copier's default `.copier-answers.yml`, so that a second template can live in the same repository with its own (see below). Copier only finds a non-default answers file when you name it; without `-a` it stops and changes nothing.

**Scripted updates.** In a script or CI, add `--defaults`, so a question new to the project takes its default instead of waiting at a prompt.

**Changing an answer.** Pass it on the update, for example turning on the sensitive-content kit:

```bash
uvx copier update --trust -a .copier-answers.syntek-author.yml --data INCLUDE_SENSITIVE_CONTENT=true
```

Turning an option off removes every file that option generated, seeds included, even ones you have filled in — they survive only in your git history — and leaves every file you created yourself, except one at a path the option generates (which a repository adopted additively can have: copy it out first). Copy out and commit anything you need first: every update prints a list of what each option-off deletes before it asks its questions, and the generated `README.md` names the files for that project. After any option change, edit by hand the seeds that describe your options (`README.md`, `CONTEXT.md`, `.claude/CLAUDE.md`, `.claude/rules/syntek-author/00-project.md` under `## Brief`, `.claude/settings.json`, `.gitignore`), because an update never rewrites a seed.

The document families work the same way. Pass the whole list you want, for example adding `msp-scp`:

```bash
uvx copier update --trust -a .copier-answers.syntek-author.yml \
  --data 'BUSINESS_FAMILIES=[business, legal, email, accounting, social-media, msp-scp]'
```

A family you leave out of the list loses its template files — its folder's signposts, `library/docs/reference/<family>-standards.md` and its sub-documents (`EMAIL-ANATOMY-AND-NAMING.md`, `MSP-SCP-POLICY-SUITE.md`), its `<family>-documents` skill and its create workflow, including your edits to any of these files — and keeps every other document you wrote in its folder. No family folder ships a seed. In a repository adopted additively, a file of yours at the family's template path (its skill, its folder pairs) is deleted with it: copy it out first. `business` cannot be left out.

`DOC_TYPE` cannot change: an update that answers it differently stops before touching a file, because the content layer holds your work and Copier only moves what it generated. A different variant is a new project.

A project rendered from a local clone at `HEAD` (see [Generating a project](#generating-a-project)) updates with `--vcs-ref=HEAD` added to the command above, until a newer release tag exists.

**Migrations.** When a release moves a folder that can hold your work, or the place a setting you can change is read from, the update runs a migration script from the template after it has written the new tree. It moves a file, or writes a value into the seed the same release delivered, only where exactly one result is right and the destination is free; it never overwrites or deletes a file, and it prints what it moved or changed, what it left, and every line that still names an old path or gives old guidance. A migration runs only when the update crosses the release it belongs to, so it reaches you from that release's tag (an update to an untagged `HEAD` still numbered below it does not run it), and a later update, such as one that adds a family, does not run it again. The update's own copy of the template is gone when it ends, so each script ends by printing the command that runs it again from the project root: a clone of the release, then the script.

**An `.agents` link outside the project.** One pair of migration steps runs on every update and is keyed to no release (DESIGN.md D44, D48). Copier refuses to render anything beneath an `.agents` link that resolves outside the project, `--exclude` included, so where `.agents` is such a link (to an agent tree of your own beside the project, say), the update renames it to `.agents.syntek-held` before the render and back afterwards: the net change is zero, and its target is never followed, read or changed. A real `.agents/` folder whose `skills` link points outside needs nothing. If an update stops before it ends (a refused answer, Ctrl-C at a question, or Copier failing as it cleans up after the render), the link stays held as `.agents.syntek-held`, and the next update refuses the changed tree; where the link is committed and the update stopped after its render, Copier has already put an identical `.agents` link back. Put the link back from the project root, in a POSIX shell (Terminal on macOS and Linux, Git Bash on Windows; never PowerShell's `rm`), before anything else, and before discarding the stopped update with `git reset --hard` and `git clean -fd`, which would delete a held link Git does not track. First check what stands at `.agents`: `ls -ld .agents .agents.syntek-held`. Where it shows no `.agents.syntek-held`, nothing is held: stop here and change nothing. Where `.agents` is a link (its line shows `->`), remove that link alone with `rm .agents` (never `rm -r`, never a trailing slash); where it is a folder or a file, move it aside to a name nothing holds yet (`ls -ld .agents.from-update` finds nothing) with `mv .agents .agents.from-update` (no trailing slash), which holds what the update wrote (check it, and delete nothing in it that is yours). Then, once `ls -ld .agents` finds nothing, run `mv .agents.syntek-held .agents` (no trailing slash). Never run that `mv` while `.agents` stands: it would put the held link inside it, and inside the folder outside the project where `.agents` is a link. Then update again; where `git status` still shows changes (a stop after the render), discard the stopped update first: run `git clean -n -d`, a dry run, move out of the project anything of yours it lists, then `git reset --hard && git clean -fd`. Where the held link was committed beside an identical `.agents` link, the next update moves nothing, says so, and asks you to remove the held link (`rm .agents.syntek-held`), commit, and update again. `copier update --pretend` still refuses such a project, because a pretend run skips migrations. A copy runs no migration: see 'An existing `.agents` folder' below.

**Every project, updating from v0.1.0.** Brief values (audience, reader test and the variant's answers) are now read only from `.claude/rules/syntek-author/00-project.md` `## Brief`; the migration copies a value you changed in `.claude/CLAUDE.md` Section 1 where that is unambiguous and lists the rest. A brief question you answer again during the update itself (with `--data`, or a new answer at the prompt) keeps that answer in `## Brief`: an older hand edit is listed as a conflict, never written over it. `migrations/v0.2.0-project-settings.sh` compares `## Brief` with `.claude/CLAUDE.md` Section 1, the reader test in `.claude/MEMORY.md`, the trading name in `standards/brand/disclaimers.md` and the style sheet's `## Project settings`, and also lists each line of your seeds that still gives v0.1.0's guidance (a numbered section of `.claude/CLAUDE.md`, 'never edit' on the whole rules folder, the trading name's old home), with the v0.2.0 wording to put in its place. Change those lines by hand.

**Business, updating from v0.1.0.** v0.2.0 replaces v0.1.0's six folders under `library/src/` with the document families. The update asks `BUSINESS_FAMILIES` for the first time (`--defaults` takes every family but `msp-scp`), removes the old folders' signposts, and runs `migrations/v0.2.0-business-families.sh`, which moves what you wrote in them: `proposals/` → `business/`, `contracts/` → `legal/`, `policies/` → `business/` (or `msp-scp/` when you choose it), `correspondence/` → `email/` (a client's letters from `client-docs/` into `client-emails/`), `finance/` → `accounting/` and `marketing/` → `social-media/`, keeping each file's sub-path, so a kept example proposal lands in `library/src/business/drafts/example-proposal/`. A file whose destination already exists, whose family you did not choose, or which git ignores where it is but would not ignore where it would go, stays put and is named. The old folders' signposts are deleted even where you edited them; your lines remain in git history. The migration lists each one with the file in its family that takes your lines (`git show HEAD:<path>` recovers them), each moved client folder or template the new folder's `CONTEXT.md` does not yet name, and each email to file into its `client-emails/<client>/<family>/` folder. Afterwards, point each listed line (unit briefs, ledger entries, your notes) at its new path, and commit.

**Every project, updating from v0.2.0 or earlier.** From v0.3.0 the ledger records each section's original and every revision, and `make compare` prints them. A section worked before the update has no revision record: `make compare` shows it with the stages its entry holds — an AI-drafted section from its AI original to its final, every change unattributed and in grey; an author-drafted one as its final alone — and says the rest were not recorded. Nothing is migrated: no file moves, the new parts of an entry are optional, and an old entry is never backfilled, because nobody can say now who made each change. Such an entry keeps its decision rows and Author final as before; only a redraft of the section starts a new record. A section whose entry is first written after the update has its full record from the start.

**Every project, updating from v0.4.0 or earlier.** The update asks two new questions and adds two MCP servers (DESIGN.md D50, D53, D54):

- **`DATA_STORE`.** With `--defaults` it records `repo`, so your binary files stay in the repository as before and only template files change: the data-root tool and its map, the rules (`.claude/rules/syntek-author/09-data-root.md` is new) and the `Makefile`, which gains `make root` and `make files-*`. Where the other syntek template's answers file (`.copier-answers.syntek-media.yml`) already records a store, the project takes that store instead, and a first answer that differs from it is refused. To move the files out later, update with `--data DATA_STORE=external`, set up each machine ([Binary files and the data root](#binary-files-and-the-data-root)), then run `make files-plan`. Choosing `external` delivers the three nested `.gitignore` files and moves and untracks nothing; where you already have your own `library/src/.gitignore`, `research/src/.gitignore` or `proposal/src/.gitignore`, it comes back with conflict markers and the update report lists it under `CONFLICT`: merge your lines with the template's.
- **`DATA_PROVIDER`** replaces `INCLUDE_DRIVE_SYNC` (business, below). A book project records `none`, or the other syntek template's answer.
- **The MCP servers.** `.claude/settings.json` gains the eight asks (those you do not allow) and the deny, once each, and `.mcp.json` and each client file you have gain the two servers, once each ([MCP servers](#mcp-servers-scrapling-and-code-review-graph)). The update report then prints the permissions script's `--write` line: run it, and the next update adds the servers to `opencode.json` and `.gemini/settings.json`, which wait until they hold the servers' asks (where you allow a server's tools in `settings.json`, the report says how instead).
- **The guard** is never wired into an existing project: add it by hand ('The guard' under [Binary files and the data root](#binary-files-and-the-data-root)).
- **The v0.5.0 report.** `migrations/v0.5.0-data-root.sh` runs before the update report, moves nothing, and prints under `▸ v0.5.0 migration — the data root and the provider (DESIGN.md D50, D53); report only`: the store and provider this template and the other syntek template record (`not yet asked` where a record holds no store); the binary files Git tracks in each filing folder, with counts and sizes; under `repo`, any file of yours at a data-root ignore path; whether `.claude/settings.json` wires the guard, and the entry to add if not; the next command; every Drive workflow the answers no longer manage, and each one from before v0.5.0 that the update deleted, which lacks the store guard step (the update report offers to restore any you had edited, and a restored copy runs unguarded); and every line of a seed you already have that still names `INCLUDE_DRIVE_SYNC` or counts the rules as `01-` to `08-`, with its v0.5.0 text. Change those lines by hand.

To keep the binary files outside the repository from then on:

```bash
uvx copier update --trust -a .copier-answers.syntek-author.yml --data DATA_STORE=external
```

**Business, updating from v0.4.0 or earlier.** `INCLUDE_DRIVE_SYNC` is gone. A recorded `true` becomes `DATA_PROVIDER` `google-drive` and keeps the Drive workflows, with the template's changes merged into your edits and the store guard step added to each; `false` becomes `none`. The workflows stay only while `DATA_PROVIDER` is `google-drive` and `DATA_STORE` is `repo`: any other answer deletes `.github/`, your edits included, and the update report lists each edited file with a command to restore it. Beside another syntek template that already records `DATA_STORE` external, the update takes `external` too and cannot answer `repo`, so it deletes the workflows. A Copier settings value for `DATA_PROVIDER` or `DATA_STORE` replaces these defaults ([Providers](#providers)), and `--data INCLUDE_DRIVE_SYNC=…` is now ignored.

Commit `.copier-answers.syntek-author.yml` and never edit it by hand; it is the record every future update merges against.

## Adopting an existing repository

There is no `copier adopt`. Adoption is a `copier copy` into the repository you already have, in one of two modes:

- **Moving adoption** (`copier copy --overwrite`): the template takes over its own paths, and the adoption script first moves your work into the template's layout. Choose it for a young repository, or one already close to the template's layout, whose governance the template should own from now on.
- **Additive adoption** (`copier copy --skip '*' --skip-tasks`): every file you have stays exactly as it is, nothing moves, and the template's files are added beside yours; `.claude/rules/syntek-author/00-project.md` then tells the template where your repository keeps things. Choose it for an established repository with conventions of its own that work — its own skills, a project `CLAUDE.md`, workflows numbered in its own series, a Drive or issuing practice — or one holding confidential material nobody should reorganise. **The caveat:** to Copier, a file you keep at a template path is a template file, so unticking a family or turning an option off on a later update deletes it, and a kept file the template later changes comes back with conflict markers (keep your version). Steps 5 and 6 below say how to meet both.

Either way, seeds you already have (`.claude/CLAUDE.md`, `MEMORY.md`, `settings.json`, `README.md` and the rest of class 2) are never overwritten, and `SEED_EXAMPLES=false` keeps an invented example out of a repository with real work in it.

Both modes also answer `DATA_STORE=repo` (DESIGN.md Section 8): an adopted repository usually holds tracked binaries, and they stay in the repository until you opt in to the data root and copy them out with `make files-plan`. Where another syntek template in the repository already records a store, leave `--data DATA_STORE=repo` out and drop `DATA_STORE` from the answers file: the copy then takes that template's store, and `adopt.sh` prints the command that way and says so. In the additive preview, an `--answers` file that records `DATA_STORE` (the examples' `repo` line, say) is the copy's own answer, so `adopt.sh` then prints the copy with no `--data DATA_STORE`, which would override it, and says so; where that store contradicts the one the other syntek template's answers file (`.copier-answers.syntek-media.yml`) records, it stops before rendering (exit `2`), because Copier would refuse the copy. `adopt.sh` also names a file of yours at a path where a data-root ignore file would land, and a kept Drive workflow, for which you answer `DATA_PROVIDER=google-drive` with `DATA_STORE=repo`. A kept `.mcp.json` gains the two MCP servers, once each, in its own text, from the moving copy or from the first update after an additive one; a git-ignored one is never read, and the report says so.

### Moving adoption

1. **In the repository you are adopting, make a branch.** Commit or stash anything outstanding, so `git diff` shows only the adoption.

   ```bash
   git switch -c adopt-syntek-author
   ```

2. **Run the advisory script** from a clone of this template. It reports what it would move and changes nothing:

   ```bash
   bash /path/to/syntek-author/adopt/theology.sh          # or fiction.sh, business.sh
   ```

   Then run it again with `--apply`. It performs only the moves that have exactly one correct destination — `workspace/handoffs` and `workspace/learning` to the root, `workspace/maps` to `planning/src/maps`, `voice-and-tone.md` to `voice-notes.md`, chapter files that are still stub briefs to `planning/src/units/`, flat `docs/*.md` guides to `docs/project/`, bespoke workflows to `workflows/local/`, `status: stub` to `outlined`, and the section sign to 'Section' in governance files — and reports everything else for you to decide, including (business) every folder under `library/src/` that is not one of the document families. It never overwrites and never deletes, and a second run is a no-op. Review and commit the moves.

3. **Copy the template over the repository**, with an answers file you have edited from `adopt/examples/`:

   ```bash
   cp /path/to/syntek-author/adopt/examples/theology.answers.yml /tmp/answers.yml   # then edit every value
   uvx copier copy --trust --overwrite --data-file /tmp/answers.yml \
     --data SEED_EXAMPLES=false --data DATA_STORE=repo gh:Syntek-Dev/syntek-author .
   ```

### Additive adoption

1. **Make a branch**, as above, from a clean tree. A file at a template path that git does not hold — left by an earlier attempt, say — is kept by the copy as if it were yours; the preview marks each kept file committed, untracked or ignored, so commit what is yours and remove the rest first.

It also names every template path your ignore rules hide (with the rule that hides it), every file you keep that unticking a family or turning an option off would later delete, every template signpost added to a folder that already holds your own files, and a kept workflow that would sync the new `drafts/` folders. Every file it keeps is marked **kept, committed**, **kept, untracked** or **kept, ignored**. And it lists each **same-named** file: a template file the copy adds beside your own file of that name in a neighbouring folder, such as the template's `library/docs/reference/business-standards.md` beside your `library/docs/business-standards.md`, with the redirect line for `## Overrides` that makes every template file read yours. Its first line names the source and ref it previewed.

3. **Copy the template beside your files:**

Preview and copy from the same source and ref, or the report is not exact: the script previews its own checkout at `HEAD`, and its closing note prints the copy command for that source.

## Applying a second template

syntek-author is built to share a repository with later templates (the first planned is `syntek-media`). Six rules make that safe:

1. Each template records its answers in its own file — this one's is `.copier-answers.syntek-author.yml`.
2. Each template keeps its instructions in its own folder, `.claude/rules/<template>/`. No template updates `.claude/CLAUDE.md`, which stays yours.
3. The shared root files (`README.md`, `CONTEXT.md`, `.claude/CLAUDE.md`, `.claude/CONTEXT.md`, `.claude/MEMORY.md`, `.claude/settings.json`, `.mcp.json`, `.gitignore`, and the skills signposts) are seeds in every template: the first one writes them, and no template ever re-renders them. The agent entrypoints and client settings (`AGENTS.md`, `GEMINI.md`, `.agents/`, `.codex/`, `.gemini/`, `opencode.json`) are copy-only in both templates and byte-identical between them from syntek-media 0.5.0 (DESIGN.md D48), so from then it does not matter which template writes them; until then, whichever template copies first decides their text; every entrypoint reads every bridge present, and each template ships its own bridge, `.claude/<template>-agents.md`, its own copy of the permissions script, `.claude/<template>-permissions.py`, its own copy of the data-root tool, `.claude/<template>-dataroot.py` (the same bytes), and its own data-root map, `.claude/<template>-dataroot.json`, naming its filing folders and any roles of its own. The two MCP servers reach an existing project once, through whichever template's update runs first, and each template's rules 06 carries the same 'Web and code tools' text. Both templates' updates hold an `.agents` link outside the project aside and put it back; once both carry the family-shared migration, they hold it under the one name `.agents.syntek-held`, so the hand fix is the same whichever update stopped. Give both templates the same `AGENT_CLIENTS` answer. Each template's own ignore rules live in nested `.gitignore` files inside its own folders.
4. Skill and layer names never collide, and the shared writing skills ship only from syntek-author, with one exception: the shared working-practice files (class 5: seven skills, the two hooks with the `.claude/hooks/` signposts, and the `handoffs/` signposts) ship from every family template, byte for byte, written by whichever copies first, and refreshed by a template's update where they still hold a version that template wrote and you have not changed them; a file holding the other template's version waits for that template's update. Each template keeps its own mode files beside them (syntek-media's are named `MEDIA-*.md`, so the names never collide), and its own update report and refs (`refs/syntek-author/`, `refs/syntek-media/`), which name a file holding the other template's version as such.
5. Large binaries never sit in plain Git: generated audio and builds are ignored, and under `DATA_STORE` external binary records and issued copies are filed under the one data root each machine names, listed in the manifest format every family template shares; under `repo` they stay in Git, as before.
6. One project, one data-root layout: every template records the same `DATA_STORE`, `DATA_AREA`, `DATA_SLUG` and kind folders. A template's first answers default to the other's recorded ones and must equal them; a later difference is reported after the update, and both templates' data commands refuse until the answers agree. `DATA_PROVIDER` defaults to the other's answer, and a difference is only reported. Remove a template's answers file when you remove the template.

Apply the second template the same way, with its own answers file, and update each separately. Copier refuses to update a repository with uncommitted changes, so each command starts from a clean, committed tree:

```bash

git add -A && git commit -m 'Apply syntek-media'
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx copier update --trust -a .copier-answers.syntek-author.yml
git add -A && git commit -m 'Update from syntek-author'
GIT_CONFIG_COUNT=2 GIT_CONFIG_KEY_0=gc.auto GIT_CONFIG_VALUE_0=0 GIT_CONFIG_KEY_1=maintenance.auto GIT_CONFIG_VALUE_1=false \
  uvx copier update --trust -a .copier-answers.syntek-media.yml
git add -A && git commit -m 'Update from syntek-media'
```

## Codex, Gemini CLI, Antigravity and OpenCode

Claude Code always ships, and `.claude/` is the one tree every client reads: the rules, skills, memory and folder manuals are written once. `AGENT_CLIENTS` adds the other clients (DESIGN.md D47):

| ----------- | ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------- |
| Codex       | `AGENTS.md`                                | `.codex/config.toml`: reads `CLAUDE.md` where a folder has no `AGENTS.md`; `model` if `CODEX_MODEL` was set; the two MCP servers and their prompts; loads once you trust the project           | `.agents/skills`                   |
| Gemini CLI  | `GEMINI.md`                                | `.gemini/settings.json`: `model.name` if `GEMINI_MODEL` was set, the `ask_user` tool excluded, and MCP servers; loads once you trust the folder (folder trust is on by default)                | `.agents/skills`                   |
| Antigravity | `GEMINI.md`, and `AGENTS.md` where present | `.agents/mcp_config.json`, which declares the two MCP servers; model chosen in the app                                                                                                         | `.agents/skills`                   |
| OpenCode    | `AGENTS.md`                                | `opencode.json`: the model and provider `OPENCODE_PROVIDER` chose (none for `user`), the two MCP servers, their asks, compaction off, edit denies for PDFs, `build/` and the typesetting bases | `.claude/skills`, `.agents/skills` |

Each entrypoint tells the client to read every `.claude/syntek-*-agents.md` present: this template's bridge, `.claude/syntek-author-agents.md`, which every project has whatever it answered, and a companion template's. The bridge gives the read order no other client loads by itself (Claude's `@` imports and `.claude/rules/` are Claude Code features, and OpenCode reads no `CLAUDE.md` at all), the model tiers, and what Claude Code enforces that the others must follow by hand: hand off rather than compact, the settings file's denies, and the author's approval. `.agents/` is a real folder: its `skills` is a relative link to `.claude/skills`, so every client sees one copy of each skill, and its `mcp_config.json` is Antigravity's. `.agents` itself is never a link, because Codex's sandbox fails on one on Linux. No file carries a key, a trust level or a permission bypass, and the only MCP servers they declare are the two keyless ones every project ships ([MCP servers](#mcp-servers-scrapling-and-code-review-graph)).

**Permissions.** `.claude/syntek-author-permissions.py` (Python 3.11 or later, standard library, no network) carries the deny and ask rules of `.claude/settings.json` into the client files, where each client can express them (DESIGN.md D49). `python3 .claude/syntek-author-permissions.py` prints the plan, every rule a client cannot express and why, and every allow rule as left to the client, and exits `1` when a client file that exists lacks a rule it could hold; `--write` adds those rules, changing only the permission keys of files that already exist. A new project's files already pass. Run it after you change the denies or asks in `.claude/settings.json`. What it writes for Codex and Gemini CLI takes effect only once you trust the project; its OpenCode rules assume you start OpenCode at the project root.

**Local models.** OpenCode is the client for them. With a local `OPENCODE_PROVIDER`, `opencode.json` writes one OpenAI-compatible provider from `OPENCODE_PROVIDER`, `OPENCODE_BASE_URL`, `OPENCODE_MODEL` and `OPENCODE_CONTEXT`: llama.cpp's `llama-server` or `llama-swap`, Ollama, vLLM, LM Studio, or any other OpenAI-compatible server. Start the server first, keep `OPENCODE_CONTEXT` no larger than the context it loads, and test tool calling on a scratch repository before trusting a local model with a draft. **A warning for shared repositories:** the committed provider replaces the address of every model a collaborator has under the same provider id in their own settings (their headers and extra models merge in), and `ollama`, `lmstudio` and `vllm` are also OpenCode's own ids. Where collaborators run their own servers, answer `user` and keep the provider in each person's settings (see 'Your own defaults' above). Codex ignores a model provider in a project file, with a warning, so a local model for Codex is your user-level setting.

**Copy-only.** These files are written once (class 5 above): an update never adds or recreates them, and changes them only by adding each of the template's two MCP servers once to a file that lacks it (`copier recopy` is a fresh copy and does write a missing one), and a changed answer reaches the model table in `.claude/rules/syntek-author/05-model-allocation.md`, not the client's file. Removing a client deletes none of its files: its row leaves the model table, and the bridge stays the route. **Updating from v0.3.0 or earlier:** the update asks `AGENT_CLIENTS` with none ticked, because the project has none of the client files. Tick the clients you will use, for example `--data 'AGENT_CLIENTS=[codex, opencode]'`, to add their rows to the model table; the bridge and the permissions script arrive whatever you answer. To add a client's files, follow 'Enabling a client in an existing project' in the project's `.claude/syntek-author-agents.md`: generate a fresh project from its answers into a temporary folder and copy only the missing files.

**An existing `.agents` folder.** A copy over an `.agents/` that already holds the same `skills` link and `mcp_config.json`, as a companion template writes them, needs nothing extra. Copier cannot write a link over a directory and fails before its skip check, so when `.agents/skills` is a real directory, copy with `--exclude /.agents/skills`; `adopt/adopt.sh` adds it for you. Never rename or remove the directory to make room: integrate its skills by hand. If `.agents` is itself a link (an older layout, such as a link to `.claude`), replace it with a real folder before you copy: updating syntek-media to 0.4.2 does this for its link, or replace it by hand. Until then `adopt/adopt.sh` prints the copy with `--exclude /.agents`. Otherwise the copy fails, with `--exclude /.agents/skills` it writes `.agents/mcp_config.json` through the link into `.claude/`, and Codex's sandbox fails on the link. If `.agents` is a link to a folder **outside** the project, Copier refuses everything beneath it even with `--exclude`, so move the link alone aside for the copy and put it back, from the project root: `mv .agents .agents.syntek-held`, copy with `--exclude /.agents`, then `mv .agents.syntek-held .agents` (run that last line too if the copy stops). `adopt/adopt.sh` prints the copy wrapped in those two lines, and never moves the link itself. The link's target is never touched; updates hold and restore it for you (see 'An `.agents` link outside the project' under [Updating a project](#updating-a-project)).

## MCP servers: Scrapling and code-review-graph

Every project ships two MCP servers, pinned and keyless, in `.mcp.json` and in each client file `AGENT_CLIENTS` chose (DESIGN.md D54):

| Server              | Runs                                                                                                                                   | For                                                                                                                                                             | Asks first                                                                                                                                                                                                                                                                           |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `scrapling`         | `uvx --from 'scrapling[ai]==0.4.15' --with 'playwright==1.63.0' --with 'patchright==1.63.0' scrapling mcp`                             | fetching web pages, over plain HTTP or through a browser                                                                                                        | its six asked browser tools: `stealthy_fetch`, `bulk_stealthy_fetch`, `open_session`, `session_fetch`, `fetch`, `bulk_fetch`. `screenshot` is not asked: it loads any address it is given in a session already open, so the rules limit it to the site you approved for that session |
| `code-review-graph` | `uvx code-review-graph==2.3.9 serve --tools …` (29 tools; its cloud-embedding tool is never offered, and its six cloud keys are blank) | a local map of a repository's code (by default this project's: `tooling/`, hooks, workflows; never the prose), kept in `.code-review-graph/`, which Git ignores | `apply_refactor_tool` (rewrites files) and `generate_wiki_tool` (writes pages); `embed_graph_tool` is denied                                                                                                                                                                         |

**Use them responsibly.** Scrapling's stealth tools are built to look like a person's browser and to get through anti-bot protection. Its `real_chrome` option launches your installed Chrome with a fresh profile, `cdp_url` hands a session control of any browser that exposes DevTools at the address given, on your machine or another, and `executable_path` launches whatever program it names. Every request comes from the machine and network address of the browser that sends it. Its plain tools, `make_request` and `session_make_request`, can also send POST, PUT and DELETE requests with a body and reach addresses on your own network, and Codex runs them without asking. Given a `file://` address, they and the browser tools read files on your machine. OpenCode runs every tool the project does not ask for without a prompt (its own default allows them), the plain tools, `screenshot` and code-review-graph's `repo_root` and registry tools among them, so there the rules are the only gate. The project's rules (`.claude/rules/syntek-author/06-global-rules.md` Section 13) tell every session to give every Scrapling tool only an `http://` or `https://` address, to ask you before each of the six browser tools, to prefer the plainest tool, to send the plain tools only as a GET to a public address, never to set those three options without your word, never to get past a sign-in, paywall, challenge page or refusal on its own judgement, and to respect each site's terms of use, its `robots.txt` and the law. That is a rule for the session, not legal advice: the decision, and the responsibility for it, are yours.

**code-review-graph and other repositories.** A call may name another repository on this machine (`repo_root`), and two of its tools search every repository in a registry in your home folder; building a graph creates `~/.code-review-graph/`. The rules tell a session to do neither without your word. In a new project, commit once before its first graph build: while Git tracks nothing it scans every file on disk, ignored ones included.

**First start.** uv downloads the servers on first use (about 100 MB for Scrapling), and a client may time out once while it does. Run these yourself, in your own terminal: they warm the cache and download the Chromium that Scrapling's browser tools drive, without administrator rights:

```bash
uvx --from 'scrapling[ai]==0.4.15' --with 'playwright==1.63.0' --with 'patchright==1.63.0' scrapling --version
uvx code-review-graph==2.3.9 --version
uvx --from 'playwright==1.63.0' playwright install chromium
```

If that Chromium then fails to start for missing system libraries, `uvx --from 'playwright==1.63.0' playwright install-deps chromium` installs them, through `sudo`: run it only if you accept that. Never run `scrapling install`: it runs that step for you.

**Approval.** The template sets nothing that skips a prompt; it only adds prompts. An interactive Claude Code session asks once before it starts a project's servers; `claude -p` and the Agent SDK start them without asking (to stop that, pass `--setting-sources user` or `--bare`, or add a `disabledMcpjsonServers` entry: <https://code.claude.com/docs/en/permissions>, 'What runs before you trust a folder'). Codex and Gemini CLI load project settings only in a trusted project; OpenCode starts them when it opens the project.

**Never run `code-review-graph install`, `init` or `uninstall`** in a project. They add an unpinned entry, which offers all 30 tools (the cloud-embedding tool among them) and passes on any cloud keys in your environment, to `opencode.json` and to the Codex and Antigravity settings in your home folder; they leave the pinned, keyless entries in `.mcp.json` and `.gemini/settings.json` as they are, and add their own there only where you removed the template's. They also write text into `AGENTS.md`, `GEMINI.md` and `CLAUDE.md`, add or remove skills, hooks and a Git pre-commit hook, and write settings in your home folder.

**Existing projects.** The first update to this release adds the asks and the deny to `.claude/settings.json`, once each, and the two servers, once each, to `.mcp.json` and to each client file you have. It never adds a server you removed, never creates a file, and never reads a git-ignored file: for one of those it names the servers to add by hand. Then run `python3 .claude/syntek-author-permissions.py --write` to carry the asks into `opencode.json` and `.gemini/settings.json` (where you allow a server's tools in `settings.json`, the update report says how instead). The `/.code-review-graph/` line reaches only new projects' `.gitignore`; code-review-graph ignores its own folder anyway, so compare before you take the template's `.gitignore`.

**Removing them.** Delete an entry, and an update never adds it back. Delete `.mcp.json` itself, and the next update recreates it with both servers, as it does for every seed.

## Pronunciation audio for constructed languages

With `INCLUDE_CONLANG`, the IPA in each language's lexicon is the source of truth and audio is derived from it. Run one, or all of them before a commit:

```bash
bash .github/scripts/check-template-tokens.sh
bash .github/scripts/run-all.sh
```

`run-all.sh` renders every profile once and runs every self-test and every audit against those renders (`--no-self-test`, `--skip-integration` and `--skip-pdf` give a quicker local loop). The audits of a rendered tree take its paths: `bash .github/scripts/generate-all.sh DIR > trees.txt`, then `bash .github/scripts/shipped-variants.sh $(cat trees.txt)`. No audit sees your own data root: each unsets `SYNTEK_DATA_ROOT` when it starts, and a case that needs a root makes a temporary one. Nor does any audit's git read your global or system git configuration, as in CI, and each sets `UV_PYTHON` to `python3` where you have not set it. CI also runs `python3 migrations/family-update.py --self-test`, `python3 template/.claude/syntek-author-dataroot.py --self-test` and `python3 migrations/agents-outside-link.py --self-test`, which work in temporary folders only, renders four profiles again on the Copier floor `copier.yml` declares and compares them byte for byte with the newest Copier's renders, and runs shellcheck at warning level over every script (the same command locally: `uvx --from shellcheck-py shellcheck -S warning -x migrations/*.sh adopt/*.sh .github/scripts/*.sh template/.claude/hooks/*.sh`).

## Working on the template

Read [`DESIGN.md`](DESIGN.md) first: it is the build contract, and where any other file disagrees with it, `DESIGN.md` wins. [`CONTEXT.md`](CONTEXT.md) maps this repository, and `.claude/CLAUDE.md` is the development manual — token discipline, how to add a skill, a mode file or a gated path, and what to run before committing. Changes are recorded in [`CHANGELOG.md`](CHANGELOG.md).
To propose a change, start with [`CONTRIBUTING.md`](CONTRIBUTING.md); report a vulnerability only as [`SECURITY.md`](SECURITY.md) says.
