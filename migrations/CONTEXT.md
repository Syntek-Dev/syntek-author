# CONTEXT.md — migrations/

The scripts `copier update` runs when a project crosses a release that moved something an author may have written in, or moved where a value the author set is read.
Copier only tracks what it generated: when a release renames or retires a folder, the update takes the template's own files to the new place and leaves the author's documents behind, in a folder nothing routes to, with no conflict and no error. When a release reads a setting from a new seed, the update writes that seed from the answers, and a value the author changed in the old place silently reverts.
A migration moves the files across, or carries the value, where exactly one result is correct, and reports everything else.
A migration may also only report, where a release changes what the author must decide but nothing has one correct new home: v0.5.0's moves no file and lists what the data root means for the project.
Two family-shared scripts are the stated exceptions, keyed to no release and run on every update: `agents-outside-link.py` holds an `.agents` link that leaves the project aside, because Copier would refuse the update otherwise; `family-update.py` reports every file the update did not deliver, refreshes the shared working-practice files the author has not changed, and adds the shipped settings entries and MCP servers, once each.
Nothing here ships: `_subdirectory: template` keeps this folder out of every generated project, and `copier.yml` runs each script from the template clone through `_copier_conf.src_path`.

## Directory Tree

```text
migrations/
├── CONTEXT.md                        ← this file
├── CLAUDE.md                         ← operating rules for writing a migration
├── agents-outside-link.py            ← every update: an .agents link outside the project held aside and restored (family-shared, D48)
├── family-update.py                  ← every update and copy: the update report, the shared-file refresh, the render record (family-shared, D52)
├── family-refresh.json               ← this template's refresh list, the settings.json entries and the MCP servers the script offers (D51, D54)
├── v0.2.0-business-families.sh       ← v0.1.0's six business family folders → the D39 families
├── v0.2.0-project-settings.sh        ← every variant: brief values the author changed → 00-project.md ## Brief (never over a fresh answer)
└── v0.5.0-data-root.sh               ← every variant, report only: the store, tracked binaries, the guard, Drive workflows, stale seed lines (D50, D53)
```

## What's here

- `v0.2.0-business-families.sh` — **business projects only.** v0.2.0 replaced `library/src/{proposals,contracts,policies,correspondence,finance,marketing}/` with the families chosen in `BUSINESS_FAMILIES` (DESIGN.md D39). The script moves every file an author created in an old folder to its D44 destination — `proposals` → `business`, `contracts` → `legal`, `policies` → `business` (or `msp-scp` when it is chosen), `correspondence` → `email` (`client-docs/` into `client-emails/`), `finance` → `accounting`, `marketing` → `social-media` — keeping sub-paths, so a kept example proposal lands in `library/src/business/drafts/example-proposal/`.
  It moves a file only into a family the update delivered (its `CONTEXT.md` is there), only where the destination is free, and never moves a git-ignored file to a path git would not ignore (D42). It reports every file it left, and every line in a tracked file that still names an old folder, with file and line.
  It also lists what the update itself lost or the author must decide: each old signpost the update deleted (edits included; the lines are recovered with `git show HEAD:<path>`), each moved client folder or template its new folder's `CONTEXT.md` does not name, and, worked out from the tree on every run, a client's `## Facts` left in `legal/` (v0.2.0 reads facts from `business/client-docs/`), a LaTeX letter under `email/` (a letter under an instrument is a legal type now), an email not yet in its `client-emails/<client>/<family>/` leaf, and the v0.1.0 family headings left in the planning seeds (`document-register.md`, `review-schedule.md`, `precedence.md`). It never overwrites, never deletes a file, is idempotent, and always exits `0`.
- `v0.2.0-project-settings.sh` — **every variant.** v0.2.0's skills read the audience, the reader test and the variant's answers (Bible translation; genre; trading name, voice, jurisdiction, currency) from `.claude/rules/syntek-author/00-project.md` `## Brief` alone (D40), a seed the update writes from the answers. v0.1.0 kept them current in `.claude/CLAUDE.md` Section 1, with the reader test also in `MEMORY.md`, the trading name in `standards/brand/disclaimers.md` and the style sheet's `## Project settings`. Where a `## Brief` bullet still reads the recorded answer and those files hold exactly one other value, the script writes that value into `## Brief` and prints the change; every other difference is listed with file and line. An answer the author gave **during the update itself** is never overwritten: where the recorded answer differs from the one in the answers file before the project crossed v0.2.0 (found in git history, so a run after the upgrade is committed decides the same), `## Brief` keeps it and each older value in those files, a hand edit or the old answer, is listed as a **conflict** with file and line.
  It then lists, never rewrites, each seed line that still gives v0.1.0's guidance — a numbered section of `.claude/CLAUDE.md` cited anywhere, 'eight files' and 'never edit them' in `.claude/CLAUDE.md`, the rules tree line in `CONTEXT.md` and `.claude/CONTEXT.md`, the rules line in `README.md`, the reader-test line in `MEMORY.md`, the trading-name pointer in `brand-voice.md` and 'change them here' in the style sheet — each with the v0.2.0 text that replaces it. It edits no file but `00-project.md`, reads no git-ignored file, is idempotent, and always exits `0`.
- `v0.5.0-data-root.sh` — **every variant; report only** (DESIGN.md D44, D50, D53). v0.5.0 lets binary records live outside the repository under a data root (D50) and replaces `INCLUDE_DRIVE_SYNC` with `DATA_PROVIDER` (D53). The update records `DATA_STORE` and delivers the resolver, but moving binaries out of Git is the author's, through `make files-plan`, so this script moves nothing. It prints, the same on every run: the store and provider this template records and the other syntek template's (`not yet asked` where its record holds no store); the binary files Git tracks in each folder the data-root map `.claude/syntek-author-dataroot.json` files, by extension, with counts and sizes read from Git's objects; under `repo`, a file already at `library/src/.gitignore`, `research/src/.gitignore` or `proposal/src/.gitignore`, which choosing `external` would turn into a conflict; whether `.claude/settings.json` wires the data-root guard, which no update wires, and if not the `PreToolUse` entry to add by hand; the next command (`make files-plan` under `external`, the `--data DATA_STORE=external` update under `repo`); every tracked workflow under `.github/workflows/` that names Google Drive's API while the answers ship no `.github/`, which still runs on GitHub and would bin the Drive copies once files leave Git; and, with `file:line` and the v0.5.0 text, every seed line that still names `INCLUDE_DRIVE_SYNC` (`README.md`, `CONTEXT.md`, `.claude/CLAUDE.md`, `00-project.md`) or counts the rules as `01-` to `08-` (`README.md`, `.claude/CONTEXT.md`, `.claude/CLAUDE.md`). It writes nothing, reads no git-ignored file and never the data root or `SYNTEK_DATA_ROOT`, and always exits `0`.
- `agents-outside-link.py` — **every variant, every update; the stated exception** (DESIGN.md D44, D48). Copier refuses to render any destination that resolves outside the project, and checks that before it reads `_exclude`, so an `.agents` link to a folder outside the project (an agent tree of the author's own beside it) fails every update. Two unversioned `_migrations` entries, the first in the list and between the `# BEGIN`/`# END family-shared migrations (D48)` markers, run it: `hold` (`_stage == 'before'`) renames that link to `.agents.syntek-held` and prints the hand fix, `mv .agents.syntek-held .agents`; `restore` (`_stage == 'after'`, before every other after-stage entry) renames it back where `.agents` is absent, removes the held link where the update already put the identical link back, and otherwise reports. It never follows, reads, edits or deletes the link's target, does nothing where `.agents` is not such a link, and always exits `0`. Python 3.11 or later, standard library only; `--help` prints its docstring, and no stage or an unknown one prints its usage line. It is **family-shared**: every family template carries it byte for byte, so it names no template and no decision number, and `family-shared.json` lists it with `"scope": "repository"`. It is an exception to this folder's naming (`vX.Y.Z-<what>.sh`), to the version key and to 'never delete a file': the one file it removes is its own held link, and only beside an identical one. A copy runs no migration, so the copy recipe is in the bridge and `README.md`.
- `family-update.py` — **every variant, every update and every copy; the second stated exception** (DESIGN.md D44, D51, D52). Python 3.11 or later, standard library and git, no network; always exits `0`, turning any error into one `family-update:` line. `update` runs as the last `_migrations` entry, unversioned, at `_stage == 'after'`, between the `# BEGIN`/`# END family-shared update (D48)` markers: it renders the new version once (`copier copy --skip-tasks` from the template clone with the recorded answers), takes the old version from the project's render record in `refs/syntek-author/template` (or renders it, where no record matches), refreshes each file `family-refresh.json` lists that still equals a recorded render, and writes one the project never had (no commit of `HEAD`'s history and no recorded render held it), so a file the author deleted stays deleted and one a skipped refresh never wrote arrives (a hook it writes is set to mode 755; a file it cannot write is reported), adds that file's `settings.json` entries (hooks, permission rules and `"autoCompactEnabled": false` where the key is absent, an owner's other value kept and reported once; each offered once and listed in the render record, so one the author removed is never added back; without a record, an entry any committed `settings.json` held counts as offered; inserted into the owner's own text, written only when an entry is added; an ask is not added where the owner allows it, `mcp__S`, `mcp__S__*` or a tool glob after `mcp__S__` included, while a deny yields only to the same rule), adds each MCP server the data lists to each listed file the new render holds and the project has (once; never creating a file; never reading a git-ignored one, whose servers are named once for adding by hand; never writing a link, a file in conflict or one that does not parse; never adding back a server the record lists as offered or `HEAD`'s history held; JSON into the owner's text, TOML as the new render's tables appended and checked to parse to exactly the plan, an unedited file as the new render's bytes; `opencode.json` and `.gemini/settings.json` only once they hold the server's ask rules, with one line giving the permissions script's `--write` command until then), prints the update report, then records the new render (its parent the old one) and points `refs/syntek-author/yours` at `HEAD`. `baseline` runs as the last `_tasks` entry, on copy only, records the first render, and adds the settings entries to a `settings.json` the copy kept (a copy over an existing project). A copy over a project an earlier version made that has no record (`copier recopy`, a moving re-adoption) first renders the versions its answers file names, so the shared files the copy kept are refreshed where unchanged. A recorded render never holds the rendered answers file, so no ref names a path of the machine. It classifies by content and never reads `copier.yml`. It writes no author file but the refreshed ones, `settings.json` and the MCP files, never the index or a branch, never commits and never deletes; the render record lists every MCP server offered (`mcp:` lines, with the hash of the value offered) and every blob it wrote (`written-blob:` lines, ` edited` where the file held the owner's edit before), so a file only the script changed is 'written once' on a later update, and a JSON or TOML file it wrote that parses equal to the new render's is delivered; `SYNTEK_UPDATE_REPORT=off` skips every render and prints only conflicts and deletions, and skips the refresh, the settings entries and the MCP servers, which the next full update delivers. A `.rej` counts as a conflict only beside a template path and only where it is new since `HEAD`; a commit at `refs/<template>/template` that is no render record, and a branch or tag called `template`, are never read as records; the project must be its own repository (in a folder inside one, one line names the shared files left missing). `--self-test` (temporary folders only) and `--help`. It is **family-shared**: every family template carries it byte for byte, so it names no template (it reads the name from `.copier-answers.<template>.yml`) and no decision number, and `family-shared.json` lists it with `"scope": "repository"`. Both family scripts run through `_copier_python`, the interpreter running Copier.
- `family-refresh.json` — **this template's data, not family-shared**: `{"format": 1, "template": "syntek-author", "refresh": [<paths>], "settings": {"autoCompactEnabled": false, "hooks": {…}, "permissions": {"deny": […], "ask": […]}}, "mcp": {"servers": […], "files": {<path>: [<key path>]}}}`. `refresh` lists the D51 shared files the script may replace; `settings` lists the hook entries, permission rules (the four path denies, D54's `embed_graph_tool` deny and its eight asks) and top-level values it may add to an existing `.claude/settings.json`, add-only, and never the data-root guard (D50: new projects only); `mcp` names the two D54 servers and the key path of each of the five MCP files (`.mcp.json`, `.agents/mcp_config.json` and `.gemini/settings.json` at `mcpServers`, `.codex/config.toml` at `mcp_servers`, `opencode.json` at `mcp.servers`), whose values the script reads from the new render; an entry is offered only where the new render's `settings.json` also holds it (a top-level value with the same value), so each must be in the seed `template/.claude/settings.json` as well (`shipped-seeds.sh` check 22). `"autoCompactEnabled": false` is added only where the owner's file has no such key; an owner's other value is kept, and the copy or update prints one line saying the handoff hooks assume false and how to set it. The format is shared with every family template; the content is each template's own.
- **How each runs.** One `_migrations` entry per script in `copier.yml`, keyed by `version:` and run at `_stage == 'after'` (the two family-shared scripts apart). Copier runs it only when the update crosses that version, read from the template's git tags; an update to an untagged `HEAD` still numbered below the version does not run it, and a later update (choosing a family, say) does not run it again.
- **By hand.** The update's own copy of the template is deleted when the update ends, so each script ends by printing the command that runs it again from the project root: a clone of the release from the source in the answers file, then the script, `{ test -d "${TMPDIR:-/tmp}/syntek-author-v0.2.0" || git clone --depth 1 --branch v0.2.0 <source> "${TMPDIR:-/tmp}/syntek-author-v0.2.0"; } && bash "${TMPDIR:-/tmp}/syntek-author-v0.2.0"/migrations/<script>.sh`. `--help` prints its header. The outside-link script prints its one-line hand fix, an `mv`, instead, and `family-update.py`'s report ends with `git log -1 --format=%B syntek-author/template`, which prints it again.
